# 工作区 · 必知

> 给以琳读，10 分钟。读完你能 hold 住伏羲怎么管"门客在哪干活"这件事，
> 能用四个问题扫任何工作区方案，能拍板留给你的 5 个产品口味题。
>
> **不讲** git 命令、文件系统机制、内部数据结构。这些不归你管。

---

## 一、为什么伏羲要管"工作区"

Karpathy 那条推（已沉淀到 [Decision 18](../decisions/18-agentic-engineering-collaboration.md)）：
**Agent 提速时仍要保住质量、安全、可维护。**

这句话落到伏羲，就是 review 时盯**四个问题**：

1. **归属是否隔离？** —— 这个改动落在哪？谁在动？说不清就是设计有洞。
2. **行为是否可审计？** —— 谁干了什么、什么时候、改了哪些字节？看不到就是黑箱。
3. **失败是否可恢复？** —— 出错能回去吗？回不去就是危险。
4. **结果是否可验证？** —— 怎么知道做对了？验不了就是赌博。

工作区是这四问的基座——没有清晰的工作区，四问都答不出来。

## 二、最重要的两个名字

**canonical**（中：真本）—— 你的真项目目录，比如 `~/erp`、`~/fuxi`。你在里面 IDE 打开、`git pull`、人类直接编辑的那个地方。**唯一真本**，伏羲不动。

**sandbox**（中：沙箱）—— 门客的副本工作区，比如 `~/.fuxi/projects/erp/sandboxes/luban/`。从你的 canonical 派生出来，跟 canonical **共享 git 历史**，但鲁班在自己的 branch 上随便干，不污染你的真项目。

类比：

```
canonical                    =  你家厨房（你做菜的地方）
sandbox（鲁班的）            =  鲁班自己的厨房（按你菜谱练手）
canonical 跟 sandbox 共享    =  共享同一本菜谱（git 历史）
鲁班练完想给你看             =  端一盘菜过来（玄女 review → 合进 canonical）
```

记住这两个词，下面所有概念都围绕它们。

## 三、5 层工作区

伏羲把"门客在哪干活"分 5 层，按"是否动文件"+"是否要 git 历史"+"是否长期保留"切：

### L-1 · scratch（脚踏地）

跟 repo 完全无关的活。比如门客帮你"用 polars 把这个 csv 转一下"。
- **落在哪**：临时目录，活完即删
- **生命周期**：任务完即销毁
- **例子**：表格转换、脚本计算、读张图、做个一次性图表

### L0 · no workspace（一行命令）

就一行 Bash，根本不需要工作区。
- **落在哪**：随便哪个 cwd
- **生命周期**：进程级
- **例子**：`ls erp`、`echo X`、`date`、`curl ...`

### L1 · read-only mount（只看不改）

门客只看代码 / 读文档，**不写**。
- **落在哪**：直接挂 canonical 或 sandbox 的副本，**只读权限**
- **生命周期**：任务级，无清理
- **例子**："搜一下 fuxi 里 EventBus 怎么实现的"、"对比 erp 和 fuxi 的派活逻辑"

### L2 · ephemeral worktree（一次性活）

一次性的改动，可能 commit、可能不 commit。比如 hotfix、试水改造、一锤子修 bug。
- **落在哪**：`~/.fuxi/projects/erp/ephemeral/<task-id>/`
- **生命周期**：任务完后**封存 24 小时**（你随时能去看 / 复活），然后自动清掉
- **例子**：今早我们做的 bug-sweep（修 3 个 bug、commit 完就完事）

### L3 · persistent sandbox（长期门客）

某门客**长期跟某项目共生**。比如鲁班是你 erp 的常驻工程师。
- **落在哪**：`~/.fuxi/projects/erp/sandboxes/luban/`
- **生命周期**：长期保留，跨任务带状态（编译缓存、未完成 WIP 都在）
- **例子**："鲁班继续修 ERP-1066"、"鲁班把上周那个未完的 feature 收尾"

### 关系图

```
           你 / 用户
              ↓
        canonical（~/erp）           ← 唯一真本
              ↓ git 共享历史
       玄女把活派给鲁班
              ↓
   鲁班的 sandbox（L3）             ← 长期工作区
        ↓ fork off 一次任务
   ephemeral worktree（L2）        ← 任务完封存 24h 后清
   或者只挂载读读（L1）
   或者跑一行命令（L0）
   或者跟 repo 没关系（L-1）
```

## 四、术语速查（≤ 13 个）

| 词 | 中文 | 一句话 |
|---|---|---|
| canonical | 真本 | 你的真项目，比如 `~/erp` |
| sandbox | 沙箱 | 门客的副本工作区 |
| worktree | 工作树 | git 让一个仓库在多个文件夹同时 checkout 不同 branch |
| branch | 分支 | git 里一条独立的开发线 |
| commit | 提交 | 把改动正式存档成一个版本 |
| merge | 合并 | 把一个分支的改动并到另一个分支 |
| rebase | 移基 | 把一个分支的根挪到新位置（常用来"追上 main"） |
| fork off | 分叉 | 从某点开新分支独立演进 |
| ephemeral | 短暂 | 一次性、用完即弃 |
| persistent | 持久 | 长期保留 |
| WIP | 在做 | "work in progress"，改了但没 commit 的脏状态 |
| GC | 自动清 | "garbage collection"，自动把过期工作区删掉 |
| quota | 配额 | 限额（磁盘、并发数） |

## 五、Review lens：四问怎么用

将来任何人（包括我）给你一个 workspace 方案，拿这四问扫一遍：

**走一个真实场景**——"鲁班来修 ERP-1066"：

| 问 | 答 | 通过？ |
|---|---|---|
| 1. 归属是否隔离？ | L3 sandbox `~/.fuxi/projects/erp/sandboxes/luban/`，鲁班的 branch `luban/erp-main` | ✓ |
| 2. 行为是否可审计？ | commit 走 `鲁班 <luban@fuxi.local>` + Co-Authored-By 你；事件流上有 `WorkspaceMutated` / `WorkspaceCommitted` 事件 | ✓ |
| 3. 失败是否可恢复？ | commit 之前的改动 git reset 可回；commit 之后 git revert | ✓ |
| 4. 结果是否可验证？ | 鲁班 commit 完，玄女发 PR review 事件，跑 cargo test，你 review 后才合进 canonical | ✓ |

四问都过 = 这设计 OK。任何一问答不出来 = 有洞，得改。

## 六、留给你拍板的 5 个产品口味题

我先按下面 default 实装。你读完想改的就一句话，我调；不回我就按 default 走。

| # | 题 | 我的 default | 反方案 |
|---|---|---|---|
| 1 | 鲁班的 sandbox 正在跑活，又来一个新任务给鲁班怎么办 | **fork off 一个 L2 ephemeral 给新任务**（鲁班"分身"，主活继续） | 串行排队（鲁班空了才接新活，简单但慢） |
| 2 | 鲁班的 sandbox 有改了一半没 commit 的 WIP 时，新任务来了 | **自动 stash 成 `wip/<old-task-id>` 分支**，PWA 上能看到"鲁班还有 N 份未完成 WIP" | 拒收新任务直到你手动收尾（更安全但阻塞） |
| 3 | 你在 `~/erp` 上 `git pull` 拉了 origin 新东西，鲁班 sandbox 还在老 base 上 | **玄女在新任务开始前自动 rebase sandbox**（只动 sandbox 不动 canonical），rebase 冲突就降级提示 | 始终先提示等你确认要不要 rebase |
| 4 | 一个任务要跨多个 project（比如同时读 erp + 写 fuxi） | **支持**，task 必须显式声明 `workspaces: [{project, layer}, ...]` | 不支持，跨域分析做不了 |
| 5 | mac 上的鲁班 vs home 服务器上的鲁班 | **per-node 独立 sandbox**，互不知道；跨节点 = 新节点上从 canonical 重新 fork（首次慢，之后跟单节点一样快） | 跨节点同步 sandbox state（实现复杂、易冲突） |

读完这五条你能直觉判断每条接不接。**默认接受不用回**。

## 一句话总结

> 工作区是伏羲让门客**有归属、有审计、能恢复、能验证**地干活的物理基座。
> 5 层从轻到重：scratch / no-workspace / read-only / ephemeral / persistent。
> 用 Decision 18 四问扫任何方案。
> 5 个产品题留给你品。
