# 门第

## 一、立宅

很久以前——其实不太久——有一位主人。他想做太多事，又不愿亲自下场。他不再雇仆人，他要养一支门客。

主人请来一位女管家，唤作玄女。他对玄女说：「此后我只跟你说话。家里的事，你拿主意；门客做什么、谁先做、做坏了怎么收拾，你定。凡有事，我只问你。」

玄女问：「那门客直接来禀我吗？」

主人说：「不。门客嘴笨，写下来的字才作数。说出口的话，风一吹就没了，跟没说一样。」

这是这座宅子的第一条规矩。

## 二、门客

门客陆续到了。

来了几个会写字的书生——他们识文断句快，会查典籍，会抄录长篇——他们是门客其一。
来了几个会盘账的——他们是其二。
将来还会有画图的、修琴的、拳脚的——位置都给他们留着。

每个门客脾气不同。书生话密但啰嗦，账房话少但精准，还有一位画师——他干活的时候你不能打断他，他正画一笔，你过去拍他一下，他得重新起手。

玄女把门客分了等。粗活的、细活的、挑头的，各有各的牌子，叫「角色」。

## 三、信差

家里所有的字条都走一条道。

门客的字条不直接递到主人手里，先递给玄女；玄女抄一份让主人备档，再决定给谁、怎么回。

字条写在一张特制的纸上，纸有固定格式——从哪儿来、到哪儿去、说什么、什么时候说的——没这格式不收。这是宅子的第二条规矩。

## 四、账房

宅子里有间屋子从来不锁。

里头摆着一本账，所有家事都往里记：谁今天来了，谁今天走了，谁说了什么，谁干了什么活，谁出了什么岔子。

只能添，不能涂。涂了的就是篡改家事，是大忌。

主人哪天想知道某时发生了什么，翻这本账就行；新来的门客想知道这家以前怎么过日子，从头读账本，能跟上。

这本账是宅子的第三条规矩。

## 五、瞭望塔

宅子角上盖了一座瞭望塔。

里头不住人，挂了一面镜子。镜子照得见全宅每个院子里此刻在干嘛——谁在写字，谁在等饭，谁在打瞌睡。

主人累了或者疑心了，就上塔看。镜子是即时映出来的，不是有人每隔一炷香跑去各院打听一遍再回来报。打听这种事，宅子里禁——这是宅子的第四条规矩：要照见，不要打探。

## 六、规矩之外的事

但宅子也不是都好。

有一回，玄女派一个门客去远处的别院办事。那门客办完了，照规矩写字条回来。可那条山路上修了一道关卡——那是另一家管的，和咱们宅子无关——它把每张字条都拆开看一遍，看不懂的就扣下。门客写得太「内部」，关卡看不懂，就扣了。门客在那干等，玄女这边以为他还在路上，主人那边问起，玄女只能说「还没回信」。后来才查出来：得在字条上额外贴一个特定的封口，关卡才放行。这事在宅子的规矩里写下了，但每回新开一条山路，伙计都得自己记得贴。一直到现在，没人贴的时候还是会卡。

还有一次，账房新来的小厮，给两条没写全的家事按了「今天」的章，可这两件事其实是上个月就发生的。账上一翻，时序乱了。修也能修，但要先去查那一夜账房值的是谁。

还有一个门客，被打发去了一个山外的别院。山外下大雪，他三天没回信。规矩说「超过半天没心跳就算掉线」，玄女知道他掉线了，可账上还写着他在岗。要是这时候有新活按「找一个空闲的、能干这活的人」去派，就可能派给他了——派出去，活掉海里。

还有玄女自己。宅里有条规矩：闲了十分钟的人就请他走。这条规矩本是给门客定的，可玄女一开始也在这条规矩的网里——有一天她真就被自家规矩差点请走过。后来主人补了一句：「这条规矩对玄女不作数。」补丁打上了，但当初没想到，是教训。

更细的还有：曾经有一阵，门客送来的一句话，被两个不同的小厮转译了两遍，主人的桌上同一句话出现两次；门客交活的时候规矩说「要原子地一步到位」，可早期写的几个交接是两步——找到人，再派出去——并发一来，同一个活派给了两个人。这些都是后来一道一道补上的。

宅子规矩好，门客壮，瞭望塔亮——但宅子也是一砖一瓦砌的，瓦缝里藏着尘。

## 七、扩张

门客越来越多，宅子也不止一处了。

主人在城里有一所宅，山里也有一所。两所宅子里都有门客，玄女在哪一所都能调动。门客的字条会过一条加密的山路从一所走到另一所。玄女在城里坐镇，山里的门客办完事字条照样飞回来。

字条上盖的章是同一个章，账本是合在一起的一本，瞭望塔在哪一所都看得见两所。

## 八、外人

这宅子没招客。

但宅子在城里开了一扇小门，主人偶尔从外头不在宅里的时候——比如路上、比如船上——可以从那扇小门给玄女送一张字条，玄女回他。这扇小门有自己的钥匙——主人随身带着，别人拿不到。

外人想从这扇门进来，进不来。

## 九、何为门第

到这里你大概看出来了。

这不是一座宅子。

那张特制的纸，是 A2A 协议。
那本只能添不能涂的账，是 SQLite 的事件日志。
那座瞭望塔，是 EventBus 的实时订阅。
那个不接见门客只跟玄女说话的主人，是用户。
那个从外头小门递字条的「路上的主人」，是手机上的 PWA。
那个被扣字条的山路关卡，是 macOS 上 Clash 的 TUN 模式吃 127.0.0.1。
那两条按了「今天」印章的旧家事，是 `created_at` 被 `now()` 回填的两条 task。
那个雪山里失联三天还挂在岗位上的门客，是 home 节点心跳挂掉 3.7 天但 worker 还在 registry 里等着被派活。
那个差点被「闲十分钟就请走」规矩请走的玄女，是 `IdleGcTask` 差点把 xuannv 收掉。
那两个把同一句话转译了两遍的小厮，是 cc stream-json parser 在 `AssistantText` 和 `ResultSuccess` 各发一次 `AgentResponded`。
那两步派活、并发会双派的旧交接，是 `find + set_status` 不原子，被 `claim_*_by_*` 替掉。

这座宅子，叫伏羲。

那位女管家——玄女——是伏羲里只跟你对话的那个 agent。
那些门客——书生、账房、画师——是 cc / codex / gemini-cli 的 headless 适配。
那条规矩「嘴笨，写下来才作数」——是公理一：headless agent 不显式沟通 = 没做。
那条规矩「主人永远有备档」——是公理二：玄女有知情权。
那条规矩「只能添不能涂」——是公理五：SQLite 是单一真相源，append-only。
那条规矩「要照见不要打探」——是公理三：实时，不轮询。

字条要走 A2A，工具要直接 shell 不走 MCP，账要留 WAL，宅子要能从城里搬到山里——这是它的形。

它不是工具，是一座宅子。一座你养着自己 agent 军团、你在玄女背后、玄女在门客背后、门客在事情背后的宅子。

宅子还在砌。瓦缝里的尘也还没扫干净。

# 后记：把寓言里讲到的东西摆出来

## 一、系统结构（宅子是怎么搭的）

- **用户** → 主人，唯一对话对象是玄女
- **玄女（xuannv）** → 顶层 orchestrator agent，调度全局
- **门客（menke）** → headless agent 适配器：cc / codex / gemini-cli
- **角色（role）** → 鲁班（luban，工程）/ 书生 / 账房 ……，dispatch 时按 `claim_idle_by_role` 选
- **A2A**（`fuxi-a2a` crate）→ agent 间协议，axum server + reqwest client
- **EventBus + 账房**（`fuxi-events` crate）→ tokio broadcast + SQLite WAL，append-only
- **瞭望塔**（`fuxi-firehose` crate）→ WebSocket + ratatui TUI，订阅式实时
- **CLI**（`fuxi-cli` crate）→ `fuxi` 二进制入口
- **Core**（`fuxi-core` crate）→ Agent / Runtime / Workspace / Event / Task traits
- **多宅**（分布式）→ home（Linux）+ zyldemacbook-pro-local（mac），加密链路打通
- **小门**（PWA / IM）→ `im.qmledmq.cn:8443`，DDNS + nginx 通配符证书 + token 认证

## 二、底层原理（七条公理）

1. **Headless agent 不显式沟通 = 没做。** A2A 是唯一出口，`println!` 出去的字无人看见。
2. **玄女永远有知情权，无否决权。** 抄送机制不得绕过。
3. **真实时，不轮询。** 观察组件订阅 EventBus，禁 poll。
4. **CLI 是工具层的唯一形态。** Agent 调用工具直接 shell，不走 MCP。
5. **SQLite 是单一真相源**（WAL + append-only）。文件系统只是执行快照。
6. **借鉴 ComposioHQ 的设计智慧，不借它的代码路径。** 语言不同天然隔离。
7. **毕设不是 DDL，是顺带。** 平台是日常用品，不为答辩压时间，也不以「demo 够用」当验收。

## 三、质量标准（门禁）

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace` 全绿
- 文档/注释/commit 中文，标识符英文
- 注释只写 **WHY**，不写废话
- **TDD 硬要求**——先写测试再实现，事后补测 = 走捷径
- 新 `EventKind` 变体必须同步五处（store / hub / tui::summarize / tui::color_for / 持久化测试）
- 新 agent adapter 三铁律：
  1. 必须 `launch_with_id(id, ...)`，不能自己 `AgentId::new()`
  2. 任何事件 pump 退出都要摊回 Idle，否则 shelf 永久 Busy
  3. find-then-act 必须原子（`claim_*_by_*`），不能两步

## 四、瓦缝里的尘（不只讲好的）

**当下还在烧的（要修）：**
- `task-a0ec427a` / `task-1b0de13b` 两条 `created_at=2026-05-01T06:37:14.432`，`last_active_at=2026-04-27` —— 时间倒挂，0.5ms 差，疑似某次写库回填用 `now()` 砸的，同时丢了 `title` / `description`。
- `home` 节点 `heartbeat_lag_ms=320300028` ≈ 3.7 天 `online=false`，但仍挂着 `luban` worker 且 `status=idle`。`claim_idle_by_role` 会乐观选中它，派活掉海里。
- `/api/tasks` 全部 `role: "unknown"`，但同一 worker 在 `/api/nodes` 里是 `role: "luban"` —— task ↔ member 写入时 role 没串过去。
- `registered_at_ms_ago == heartbeat_lag_ms`，语义不清。

**结构性的伤疤（已补，记着别再踩）：**
- VPN TUN 吃 `127.0.0.1` 反连：`spawn_claude` 注入 `NO_PROXY`，手动起 cc 也得记得加。
- 起子 cc 必清 `CLAUDECODE*` env，否则嵌套检测静默卡死。
- TUI stderr 重定向必须在 `init_tracing` **之前**，否则启动期日志退 TUI 后满屏冒。
- `Fuxi::shutdown_agent` 开头必须豁免玄女，`IdleGcTask` 别把宅子管家收了。
- macOS `TempDir::new()` 返 `/var/folders`，`git worktree list` 返 `/private/var/folders`，比对前要 `canonicalize()`。
- Codex worker busy 时不支持 follow-up；idle 时走 degrade-dispatch（Decision 04）。
- `fuxi-memory` 不能依赖 `fuxi-orchestrator`（循环），adapter 放 `fuxi-cli`。
- cc stream-json parser 双发 `AgentResponded`，加 `responded_this_turn` 去重。
- mock fixture 跟 real wire 不对齐曾让玄女历史「刷新就空」隐 bug 埋了一个月——新加反序列化 helper 先 `sqlite3 *.db` 看真数据形状。
- 18+ 条 D1-D18 详见 `docs/architecture-audit-v1.md`。

**没那么显眼但要记住的：**
- `spawn` 语义是「新建」，不去重。复用走 `dispatch_to_any(role)`，回收交 GC。
- TUI `Submit::Xuannv` 走 `intervene` 不走 `dispatch`，否则堆僵尸 task。
- dispatch pump 看到 terminal **不立即** break，500ms 超时后退，否则 M2.1 drain 塞进来的新响应没 receiver。
- Cargo.lock cherry-pick 后常坏，直接 `rm Cargo.lock && cargo build` 重生。

宅子盖完了吗？没。门客够齐了吗？还差几个。账房的瓦缝清了吗？正在清。

但宅子的样子已经能看见了：一个让你养着自己 agent 军团、你只对玄女说话、字条永远留底、瞭望塔永远亮着、城里和山里的门客同管同账的——长期住的家。

不是工具。是一座宅子。
