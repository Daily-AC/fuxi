# 玄女分身 + 完工持久队列 实装计划

> **For agentic workers:** REQUIRED SUB-SKILL: 用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐 task 实装。步骤用 `- [ ]` 跟踪。
>
> 设计源：`docs/superpowers/specs/2026-06-10-玄女分身-持久队列-design.md`。关联 issue `357da78a` + `a01cfab5`。

**Goal:** 把玄女从「单例 cc + 活跃 topic 切换」改为「按 topic 的分身池（懒启动 + 空闲回收）」，并为门客完工信号加持久队列，根治跨 topic 串味与完工信号丢失。

**Architecture:** 现状已有 topic 原语（`fuxi_core::TopicId`、im.db `topics` 表、`XuannvSwitcher`、bridge 的 `topic_watch` 过滤）。当前 bridge 对普通事件按 topic silent skip，但**里程碑事件（`is_cross_topic_milestone`）故意跨 topic 透传到当前玄女**——这就是串味根因。本计划把单玄女换成 `XuannvPool: topic_id → AgentId`，里程碑路由到**归属 topic 的分身**；分身 dormant 时完工事件落持久队列 + respawn 补发。

**Tech Stack:** Rust（fuxi-core / fuxi-orchestrator / fuxi-cli / fuxi-im）、tokio watch、sqlx（im.db migration）、async-trait。

**现状关键坐标（实装前先读）：**
- `crates/fuxi-orchestrator/src/fuxi.rs`：`xuannv_id: watch::Sender<Option<AgentId>>`（:102）、`set_xuannv`（:205）、`xuannv_id`（:211）、`xuannv_id_watch`（:226）、`shutdown_xuannv_for_handoff`（:1907 附近）。

```rust
//! 玄女分身池：topic_id → 活分身 AgentId。懒启动 + 空闲 dormant 回收 + LRU。
use fuxi_core::{id::AgentId, TopicId};
use std::collections::HashMap;
use tokio::sync::{watch, Mutex};

pub struct XuannvPool {
    max_active: usize,
    // active: 当前活着的分身。dormant 回收后从这里移除（映射不保留死 id）。
    inner: Mutex<PoolInner>,
    // watch：供 bridge 等订阅者实时读 topic→分身 全量映射（跟随 respawn 漂移）。
    tx: watch::Sender<HashMap<TopicId, AgentId>>,
}
struct PoolInner {
    active: HashMap<TopicId, AgentId>,
    // LRU 近况：topic → 最近活跃单调计数（用计数避免 Date.now 依赖）。
    lru_tick: HashMap<TopicId, u64>,
    clock: u64,
}
impl XuannvPool {
    pub fn new(max_active: usize) -> Self { /* tx=watch::channel(HashMap::new()).0 ... */ }
    pub async fn active_id(&self, topic: TopicId) -> Option<AgentId> { /* inner.active.get */ }
    pub async fn set_active(&self, topic: TopicId, id: AgentId) { /* insert + bump lru + tx.send_replace(snapshot) */ }
    pub async fn remove(&self, topic: TopicId) { /* dormant 回收：active.remove + tx 更新 */ }
    pub fn watch(&self) -> watch::Receiver<HashMap<TopicId, AgentId>> { self.tx.subscribe() }
    /// 超 max_active 时返回应被 LRU 回收的 topic（调用方负责 dormant 它）。
    pub async fn lru_victim_if_over_cap(&self) -> Option<TopicId> { /* active.len()>max → min lru_tick */ }
}
```
> `max_active` 由 `FUXI_XUANNV_MAX_ACTIVE` 注入（默认 3），在 Fuxi 构造处读 env。
