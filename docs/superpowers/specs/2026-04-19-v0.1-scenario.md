# 伏羲 v0.1 · 验收场景 spec

> 北极星：**用户在真实工作里用它**。不是答辩演示，不是技术炫技。
>
> 验收条件：用户某天做自己本来会用 Claude Code 手动做的事，这次用 `fuxi` 做了一遍，之后愿意继续用。
>
> 本文档是后续所有工作的**锚**。每个 PR / 每条必做项必须能回答"这一步把验收场景推进了多远"。推不动的延到 v0.2+。

## 1. 首次使用场景（可断言的端到端故事）

### 用户视角的铁律

**用户只跟玄女对话**。`fuxi` 是你唯一的入口命令：无参进 REPL，玄女等你说话。你**不直接 spawn 门客**——不会有 `fuxi spawn` 这种命令进你的视线，那些是玄女的内部工具（她 CC 实例通过 Bash 调用）。

- 你对玄女说："做 X" → 玄女决定 spawn 谁、dispatch 什么任务、何时回收
- 你对玄女说："停，换方向" → 玄女**打断**当前门客、调整或重派
- 你对玄女说："commit" → 玄女让门客去执行

用户视角下：**所有动作都经玄女**。下面场景反映这个铁律。

### 场景文字

```
$ cd ~/team-anya
$ fuxi

[伏羲 daemon 启动，玄女 CC 实例唤起，TUI 进入 REPL]

玄女 > 在。想做什么？

user > 看一下 apps/usage-reporter/src/parser.ts 和它的测试
       parser.test.ts。如果测试能跑通，给它加三个边界 case
       （空文件、malformed JSON、超大行数）。提交前让我看 diff。

玄女 > 收到。我让一个 dev 门客去做，干完汇报。

[右侧面板：spawn dev-#1 (kind=cc)，task T001 已派发]
[事件流实时渲染]
[T001] dev-#1 · reading parser.ts (147 行)
[T001] dev-#1 · reading parser.test.ts (89 行，12 个 case)
[T001] dev-#1 · running pnpm test -- parser
[T001] dev-#1 · basecase pass (12/12)
[T001] dev-#1 · writing parser.test.ts (+32 -0)
[T001] dev-#1 · running pnpm test -- parser
[T001] dev-#1 · all pass (15/15)
[T001] dev-#1 · 等待 commit 授权

玄女 > dev-#1 完成。15 个 case 全过，diff 32 行加 0 行删。
       要不要看 diff？
user > 看

[diff 渲染在对话区]

user > 第三个 case 的命名叫 "big_file" 太含糊，改成 "input_over_10k_lines"。
       其它的不用动。
玄女 > 收到。打断 dev-#1 当前 idle，让它改。

[介入走 cc --sdk-url 反连 control_request，dev-#1 当前 turn 作废]
[T001] dev-#1 · interrupted (reason=user_intervention)
[T001] dev-#1 · 用户要求重命名第三个 case
[T001] dev-#1 · editing parser.test.ts (-1 +1)
[T001] dev-#1 · running pnpm test -- parser (15/15 pass)

玄女 > 改好了。新 case 名 "input_over_10k_lines"。现在同意 commit 吗？
user > 同意
玄女 > 好。

[T001] dev-#1 · git add parser.test.ts
[T001] dev-#1 · git commit -m "test(usage-reporter): 加 3 个 parser 边界 case"
[T001] dev-#1 · done · commit=abc1234

玄女 > 提交完。commit abc1234。还有别的吗？
user > 没了，退出
[dev-#1 shutdown · 事件流结束 · fuxi daemon 关闭 · TUI 退出]
$
```

### 可断言的事件序列

这个场景跑完，事件库里必须能 `SELECT` 到（顺序大致如下）：

```
1.  fuxi_daemon_started
2.  agent_spawning          (id=xuannv,  role=xuannv, kind=cc)
3.  agent_ready             (id=xuannv)
4.  user_message            (to=xuannv, text="看一下...")
5.  agent_thinking          (id=xuannv)
6.  agent_spawning          (id=dev-#1, role=dev, kind=cc)   ← 玄女决定
7.  agent_ready             (id=dev-#1)
8.  task_dispatched         (task=T001, from=xuannv, to=dev-#1)
9.  tool_called             (id=dev-#1, tool=Read, path=parser.ts)
10. tool_called             (id=dev-#1, tool=Bash, cmd="pnpm test -- parser")
11. tool_called             (id=dev-#1, tool=Edit, path=parser.test.ts)
12. tool_called             (id=dev-#1, tool=Bash, cmd="pnpm test -- parser")
13. task_blocked            (task=T001, reason="awaiting_commit_approval")
14. agent_responded         (id=xuannv, text="dev-#1 完成...")
15. user_message            (to=xuannv, text="看")
16. user_message            (to=xuannv, text="第三个 case 命名改掉")
17. user_intervention_sent  (from=xuannv, to=dev-#1, mode=interrupt)  ← WS 反连 control_request
18. agent_interrupted       (id=dev-#1, reason="user_intervention")
19. task_intervention_applied (task=T001)
20. tool_called             (id=dev-#1, tool=Edit, path=parser.test.ts)
21. tool_called             (id=dev-#1, tool=Bash, cmd="pnpm test -- parser")
22. agent_responded         (id=xuannv, text="改好了，现在同意 commit 吗？")
23. user_message            (to=xuannv, text="同意")
24. task_resumed            (task=T001)
25. tool_called             (id=dev-#1, tool=Bash, cmd="git commit ...")
26. task_completed          (task=T001, result=commit=abc1234)
27. agent_shutting_down     (id=dev-#1)
28. agent_dead              (id=dev-#1)
29. user_message            (to=xuannv, text="退出")
30. fuxi_daemon_stopping
31. agent_shutting_down     (id=xuannv)
32. agent_dead              (id=xuannv)
33. fuxi_daemon_stopped
```

不要求字面一致，但**这 33 个断言点**必须能被 EventBus / SQLite 查询出来。少一个都算 v0.1 没达。

**核心新增**（17-19）：WS 反连模式的打断式介入——玄女发 `control_request interrupt`，门客当前 turn 作废，事件流留下 `agent_interrupted` + `task_intervention_applied`。没这三个事件就不叫"能介入"。

## 3. v0.1 的权限 / 沙箱姿态

- 玄女 & 门客：**全 bypass**（项目内 `.claude/settings.local.json` 已经是 bypassPermissions）
- 不做策略层审批、不做沙箱
- **唯一安全保障**：事件流实时可见，用户 Ctrl-C 整个 `fuxi` 即可暴力终止
- 用户要 commit 前的 diff 审查是**产品要求**（场景里显式要求"提交前让我看 diff"），通过 task_blocked + 玄女主动请示实现，**不是**靠工具审批弹窗

这个姿态本身就是 v0.1 的简化选择——不动权限 / 沙箱层，集中火力让场景跑通。v0.2 开始引入分层策略。

## 4. Skill 作为 profile 格式（今天新增的结构决策）

v0.1 起，门客和玄女的 profile **采纳 [Anthropic Agent Skills](https://github.com/agentskills/agentskills) 格式**：

- 每个 role 一个 folder：`~/.fuxi/skills/<role>/`
- 必需：`SKILL.md`（frontmatter + instructions）
- 可选：`scripts/` / `resources/` / `examples/`
- cc / codex / opencode 三家门客后端统一能读

**v0.1 内置两个**：

```
~/.fuxi/skills/
├── xuannv/
│   ├── SKILL.md          ← 玄女的身体
│   └── instructions/
│       └── tool-map.md   ← 告诉她 fuxi CLI 子命令怎么用
└── dev/
    └── SKILL.md          ← dev 门客
```

公理 #4（CLI 是工具层唯一形态）不变 — Skill 提供 prompt + 知识，CLI 提供 actual 工具。**不上 MCP**（token 效率）。

## 6. 未决（认识到没想清楚的）

这些留着不是偷懒，是**承认不知道最佳解**：

- **daemon 生命周期**：用户 `fuxi` 一次 = 一次 daemon，退出时 daemon 死？还是 `fuxi up` 长跑 daemon + `fuxi` 作为 REPL client？两种都合理，v0.1 先选"一次性"更简单，v0.2 有可能改。
- **REPL 中如何指名某个门客说话**：`@dev-#1 xxx` 这种是最直白的，但 v0.1 场景不需要——用户只对玄女说话。介入机制 v0.2 再加。
- **玄女的 system prompt 长什么样**：这是 Skill 内容本身。会在实施 A 时起草第一版，跑通后根据实际表现迭代。第一版不求完美。
- **事件流在 REPL 里怎么不喧宾夺主**：对话区和事件流如何共处——v0.1 用"事件在独立区域滚动，玄女的话高亮在对话区"的简单方案；真不够用再改。
- **门客失败怎么办**：v0.1 粗暴——门客崩了玄女收到 `agent_dead`，玄女用自然语言告诉用户并问怎么办。不做 restart policy。

## 7. 执行顺序

按依赖：

```
H (cc WS 升级) ──┐
                 ├─┐
A (玄女 Skill) ──┤ │
                 ├─┼─> D (REPL TUI) ─┐
B (CLI 子命令) ──┤ │                  ├─> G (集成测试)
                 │ │                  │
C (daemon IPC) ──┤ ├─> I (介入) ──────┤
                 │ │                  │
E (dev Skill) ───┘ ├─> F (task_blocked)┘
                   │
                   └─ (H 完成后 I 才能跑)
```

**可并行**：H + A + B + C + E（五条齐头并进，分别是 cc WS 升级 / 玄女 Skill / CLI 子命令 / daemon IPC / dev Skill）。  
**依赖**：D（REPL TUI）等 A/B/C；I（介入）等 H 的 `control_request` 管道 + C 的 daemon；F（task_blocked）独立；G（集成测试）最后。

估计日历时间：**聚焦 5-7 个工作日**（并行化 + claude 自己多 agent 帮忙干）。

**首个开工**：薄片 H（cc WS 升级）是最长也最硬的一条，立即启动。参照实现完整在 `/Users/e0_7/team-anya/apps/server/src/broker/backends/claude-code-backend.ts`（1066 行 TS），Rust 移植路径清晰。
