## 0. 一句话

伏羲是让个人 AI agent 军团得以有序运行的平台。用户只跟**玄女**对话（顶层 agent），她像高级谋士一样招募、分派、协调一群**门客**（cc/codex/gemini-cli 实例）干活，用户实时可见每一步，随时可以亲自介入。

## 1. 称谓表

| 词 | 指什么 |
|---|---|
| **伏羲** | 平台本身（Rust 实现的 runtime、协议、事件总线、状态库）。不做具体工作 |
| **玄女** | 顶层 agent，唯一跟用户主对话的那位。招募/分派/复盘，不亲手干活 |
| **门客** | 玄女招募的员工 agent。底层是 cc / codex / gemini-cli 的 headless 实例，套上角色 profile（PM、Dev、QA、Reviewer 等） |
| **A2A** | agent 之间唯一的通讯协议（Google Agent2Agent v1.0，2026-03 stable） |
| **抄送（CC）** | 用户绕过玄女直接对某门客说话时，玄女自动收到副本，维持世界模型一致 |
| **Firehose** | 实时向用户推送所有 agent 事件的 WebSocket 流 |
| **Worktree** | 每个 Dev 门客独立的 git 工作区，互不干扰 |

## 2. 锚点场景

所有设计都必须让这条链路跑通。这是用户对伏羲最核心的期待：

1. 用户对玄女说："我想给伏羲开发一个现代化 IM"
2. 玄女判断这是大需求，**招一位 PM 门客**（cc + PM profile）
3. 玄女**把主对话权转交 PM**；用户开始跟 PM 聊功能、对标、风格
4. 用户另开一个终端看 **Firehose**——实时显示玄女刚 spawn 了 PM、PM 正在 thinking、PM 正在写 brief
5. PM 写完 brief，把主对话权交回玄女
6. 玄女读 brief，**招 2 位 Dev 门客**（各自 worktree 隔离），派"前端"和"后端"
7. 用户刷 Firehose 看见 Dev-A 选了 Electron，**直接从仪表盘对 Dev-A 说"用 Tauri"**
8. 玄女**自动收到这条抄送**，主动反馈："收到，我已更新 brief，Dev-A 调整中"
9. Dev 推 PR；玄女招 QA 门客 review；通过后玄女回复用户"已交付"

该场景考验的能力：多角色 spawn、主对话权转交、实时事件流、抄送介入、多 worktree 并行、全流程可审计。

## 3. 拓扑

单机为主，预留云 burst 接口。

```
            用户（伏羲的主公）
                 │
                 │ 主对话（动态：可能是玄女，可能是某个门客）
                 │
          ┌──────▼──────┐
          │    玄女     │ 长驻，cc 实例 + 玄女 profile
          │  (顶层 agent)│
          └──────┬──────┘
                 │ A2A v1.0
      ┌──────────┼──────────┐
      │          │          │
  ┌───▼──┐   ┌───▼──┐   ┌───▼──┐
  │门客 1│   │门客 2│   │门客 N│ 常驻班底 + ad-hoc spawn
  │(PM)  │   │(Dev) │   │(QA)  │ 每个在独立 worktree
  └───┬──┘   └───┬──┘   └───┬──┘
      │          │          │
      └──────┬───┴──────────┘
             │ 事件流
       ┌─────▼──────┐
       │ EventBus   │ 伏羲核心：tokio broadcast + SQLite WAL 持久化
       └─────┬──────┘
             │ WebSocket
       ┌─────▼──────┐
       │Firehose UI │ TUI（ratatui）+ 可选 Web
       └─────┬──────┘
             │
             ▼
            用户（观察 + 介入入口）
```

## 4. 宏观链路

### 4.1 正常派发

```
用户 → 玄女（REPL）
    │
    ▼
玄女决策 → A2A.dispatch(agent_type, task) → 伏羲.spawn()
    │                                        │
    │                                        ▼
    │                                    进程起来，分配 worktree，A2A 握手
    │                                        │
    ▼                                        ▼
玄女拿到 agent_handle ←─── 注册到 EventBus ──┘
    │
    ▼
玄女通过 A2A send() 下指令
    │
    ▼
门客干活，每个 tool call / state transition 发一条事件
    │
    ▼
EventBus 广播 → Firehose（用户看）+ 玄女的世界模型 watcher
    │
    ▼
门客 A2A.complete(artifact)
    │
    ▼
玄女在 REPL 里告诉用户结果
```

### 4.2 抄送介入

```
用户 → Firehose UI 选中门客 X → 发送消息
    │
    ▼
InterventionProxy 收到
    │
    ├── 主路径：A2A.send(门客X, 用户消息)
    │
    └── 抄送：A2A.send(玄女, {type: "user_intervention", target: X, msg})
         │
         ▼
     玄女更新世界模型 → 主动在 REPL 反馈："收到，我已调整"
```

### 4.3 主对话权转交

```
玄女 → ConversationSwitch.transfer_to(门客X, context)
    │
    ▼
Firehose UI 的 REPL 标签切换到门客 X
    │
    ▼
用户后续输入直连门客 X（玄女收抄送）
    │
    ▼
门客 X → ConversationSwitch.return_to_orchestrator(brief)
    │
    ▼
REPL 切回玄女
```

## 5. 伏羲的三个独创赌注

ComposioHQ 和绝大部分开源项目没有这三个。它们是伏羲相对于业界 state-of-the-art 的差异，也是毕设 contribution。

### 5.1 主对话权转交（Conversation Switch）

玄女可以把"当前跟用户主对话的 agent"从她自己切到某个门客（典型：PM 接管需求澄清），也可以再切回来。这是"分工角色"真正落到交互层的机制——PM 真的跟用户直连，不是玄女模拟 PM 问话。ComposioHQ 的 orchestrator 是严格 read-only 模型，不支持这个。

### 5.2 抄送式介入（Carbon-Copy Intervention）

用户直接对任一门客说话时，玄女永远自动知道。她无否决权但有知情权和主动调整权。这保证**玄女的世界模型永远和现实一致**。ComposioHQ 的 `sessionManager.send` 直接写入目标 worker，orchestrator 不被通知——伏羲的独创语义补齐。

### 5.3 真实时 Firehose

ComposioHQ 的 lifecycle 循环是 30s 轮询（`lifecycle-manager.ts:1973`，`start(intervalMs = 30_000)`），web 前端另加 ~5s 刷新。伏羲 day 1 就是真 EventBus + WebSocket 推送，全 push 无 poll。默认**转场级颗粒度**（spawn、dispatch、deliver、block、complete 等 30+ 事件类型）。工具调用级（每次 Read/Edit）默认不推，按需订阅特定 agent 开细粒度。

## 7. 技术栈

- **Rust** stable, edition 2024
- **tokio** async runtime
- **axum** HTTP + WebSocket 服务器
- **sqlx + SQLite** WAL 模式，单一真相源 + append-only 事件日志
- **A2A v1.0 自实现**——Rust 生态无现成 SDK，自己写（同时作为毕设 contribution 之一，可考虑开源回馈）
- **cc / codex / gemini-cli** 各自 headless 模式作为门客载体（用各家官方 JSON I/O，不 pty-wrap）
- **tracing + tracing-subscriber** 底层可观测
- **ratatui + crossterm** Firehose TUI
- **clap** CLI 框架
- **Next.js** web 仪表盘（可选，后期）

## 9. 与 team-anya 的关系

### 借鉴（原则和经验）

- **`channel_send` 公理**——headless agent 不显式沟通 = 没做。伏羲里对应 A2A 的 `message.send` 和 `task.complete`
- **append-only 事件日志 + SQLite 单一真相源**——直接抄思路
- **角色 profile + prompt 分层装配**（L0-L5）——抄 Loid/Yor/Franky 的 profile 结构
- **"memory 是伤疤不是笔记"**——哲学搬过来
- **AgentBackend 抽象层的概念**

### 不取

- 飞书 IM 通道（伏羲是 CLI-first）
- 多人多租户
- 3 层 MCP 工具（伏羲用 CLI 替代 MCP 作工具层）
- 固定五角色（伏羲的角色是可扩展的）

## 11. 开放问题

- 玄女和门客的 profile/prompt 内容（角色层，不在平台设计里，实施时填）
- 云 burst 的触发策略（手动挡还是自动判断负载）——P3 开始时再定
- A2A v1.0 Rust 实现是否开源回馈社区——P4 可选

## 12. 核心公理（一票否决的基线）

1. **Headless agent 不显式沟通 = 没做。** 通讯层（A2A）是 agent 唯一出口。
2. **玄女永远有知情权，无否决权。** 用户可绕过她，但她永远被抄送。
3. **真实时，不轮询。** 任何"实时"组件必须走 EventBus 推送，不得 polling。
4. **CLI 是工具层的唯一形态，不走 MCP。** Agent 要调工具，直接 shell。
5. **单一真相源是 SQLite。** 文件系统只是执行快照。
6. **依赖 ComposioHQ 的只能是它的设计智慧和公开契约，不能是它的内部代码路径。** 语言不同天然隔离。
