# 玄女分身（按 topic 的会话隔离）+ 完工持久队列 · 设计

> 关联 issue：`357da78a`（门客事件跨 topic 串味）· `a01cfab5`（门客完工信号丢失）。
> 立于 2026-06-10。背景：当日玄女因 cc session wedge「假活 Idle」卡死 28h，
> 暴露出「完工信号 fire-and-forget、玄女不可达即永久丢」+「玄女单例致跨 topic 串味」两个根因。

## 1. 问题

当前玄女是**单例 cc session**：所有 topic 共用同一底层进程，切 topic 只换「对话回顾」上下文，
底层仍是同一个玄女。由此两个缺陷：

1. **跨 topic 串味**（357da78a）：门客生命周期事件（`AgentRequestReview` / `AgentDead` /
   `TaskStateChanged{Done}`）走全局 `SystemEventBridge`，无差别注入「玄女当前正在对话的 turn」，
   不认 topic。用户在 topic A 派的活，完成事件串味落到 topic B 的对话里。
2. **完工信号丢失**（a01cfab5）：完工/review 信号靠 fire-and-forget `intervene` + 1.7s 短重试投递，
   玄女若在窗口内不可达（忙 / 卡死 / 重启）即**永久丢失**——无持久队列在她恢复后补发。

## 2. 核心模型

玄女从「单例 1 个 cc」变为「**按 topic 的分身池**」：同一份 soul system prompt，
每个分身只看自己 topic 的对话历史 + 门客事件 → 天然隔离串味。用户视角仍是「同一个玄女、
不同对话线」（共享灵魂 + 各自记忆）。

三条已拍板地基：
- **懒启动 + 空闲回收**（不是全常驻、不是热门常驻）。
- **共享灵魂 + 各自记忆**（同一 soul prompt；分身只见自己 topic；默认互不知对方 topic 的事）。
- **持久队列 + 主动唤醒推送**（完工事件落库；目标分身睡着则 respawn + 回放 + 主动报 + push）。

## 3. 组件

### 3.1 分身池 + 生命周期（XuannvPool）

- `Fuxi` 内 `xuannv_id: AgentId` 单例 → `XuannvPool`：`topic_id → AgentId` 映射，
  外加 `watch::Receiver<HashMap<TopicId, AgentId>>` 让 bridge / 各订阅者实时跟随漂移
  （沿用现有 `xuannv_id_watch` 的 drift 机制，扩成 map 版）。
- **懒启动**：topic 首次来消息且池中无该 topic 活分身 → spawn 玄女 cc，注入
  「你服务 topic=X」addendum + 回放该 topic 历史（复用现有 bootstrap 回放，按 topic 过滤）。
- **空闲回收**：复用 `IdleGcTask`，但分身回收语义改为 **dormant 而非永久 kill**——
  TTL 到回收进程，池映射标记 dormant；下次该 topic 来消息 / 有完工事件再 respawn + 回放。
- **并发上限**：`FUXI_XUANNV_MAX_ACTIVE`（默认 3）。超限按 LRU 回收最久未活跃分身。
- **豁免改造**：现有 `shutdown_agent` / `idle_gc` 对单个 `xuannv_id` 的永久 kill 豁免，
  改为「豁免池中所有活分身的永久 kill，只允许 dormant 回收」。只有 `Fuxi::shutdown()`
  （整体下线）能真关所有分身。`shutdown_xuannv_for_handoff` 改为按 topic 作用于单分身。

### 3.2 事件 topic 路由（修串味根因）

- **dispatch 打 topic**：`Task` 加 `topic_id: Option<TopicId>`（`#[serde(default)]` 兼容旧库
  meta.json + events.db 里旧 Task JSON）。分身 dispatch 门客时，把自己服务的 topic 写到 task 上。
- **bridge 按 topic 路由**：`SystemEventBridge::handle_event` 处理门客事件时，
  从 task → topic 反查目标 topic，注入**该 topic 的分身**（而非「当前对话」）。
  目标分身 dormant → 走 §3.3 持久队列路径。
- 无 topic 的旧 task / 平台级事件 → 路由到 `general` 默认 topic 分身（兜底）。

### 3.3 完工持久队列（a01cfab5）

- **新表**（定在 **im.db**——与 `topics` / `conversations` / `notifications` 同库，
  通知本就是会话邻接数据；走 sqlx migration，跟现有 im.db 表一致）：
  `pending_xuannv_notifications(id TEXT PK, topic_id TEXT, prompt TEXT, system_origin TEXT,
  created_at TEXT, delivered_at TEXT NULL)`，索引 `(topic_id, delivered_at)`。
- **投递决策**（在 bridge 门客完工事件处理处）：
  - 目标 topic 分身**活着** → 直接 `intervene_system`（现有 retry 路径），成功即不入队列。
  - 目标分身 **dormant / 不可达** → 写入队列 + 立即 respawn 该 topic 分身、drain 队列、
    让她主动报「门客干完了」+ 发 push 通知。
- **drain 时机**：任何分身 spawn / respawn 时，先查并消费自己 topic 的未投递队列
  （`delivered_at IS NULL`），注入首 turn，标记 `delivered_at`。
- **根治效果**：完工信号持久化——玄女卡死 / 重启 / 回收后恢复，队列必补发，不再黑洞。
  与现有 `TaskStateChanged{Done}` 兜底 + idle-degrade 并存（多一层可靠性，不互斥）。

### 3.4 迁移兼容

- `general` 默认 topic（`00000000-...-0001`）= 第一个分身，行为与今天完全一致。
- 旧 events.db / 旧 meta.json 里无 `topic_id` 字段的 Task → `#[serde(default)]` 落到 `None`，
  路由兜底到 general。反回归单测：`task_deserializes_legacy_without_topic_id`（仿现有
  `task_deserializes_legacy_without_project_id` 模式，见 CLAUDE.md「加字段必加 serde default」）。

## 4. 数据流（门客完工 · 目标分身睡着）

```
门客完成 → emit AgentRequestReview{task}  (task.topic_id = A)
  → SystemEventBridge.handle_event
     → 反查 task.topic_id = A
     → XuannvPool.get(A) = dormant
     → 写 pending_xuannv_notifications{topic=A, prompt, origin=review_request}
     → respawn 分身(A) → bootstrap 回放 topic A 历史 + drain pending(A)
     → 分身(A) 首 turn 注入「门客干完了」→ 主动报 + push 通知
```

## 5. 测试策略

- **池**：懒启动只在首消息 spawn；并发超 `MAX_ACTIVE` 触发 LRU 回收；dormant 后再消息 respawn。
- **路由**：topic A 派的门客完工，只注入分身 A，不串味到分身 B（核心回归，对应 357da78a）。
- **持久队列**：分身睡着时完工 → 落库 + respawn + drain；分身卡死/重启后队列补发（对应 a01cfab5
  根因，仿当日 zombie 场景）；`delivered_at` 幂等不重投。
- **迁移**：旧 Task JSON 无 topic_id 反序列化不炸、兜底 general。
- **豁免**：idle GC 回收分身是 dormant 不是永久 kill；`Fuxi::shutdown()` 才真关全池。

## 6. 实装拆解（供 writing-plans / agent team 并行）

四块相对独立，建议 agent team 分派：
1. **池模型**：`XuannvPool` + watch map + 懒启动/dormant 回收 + 豁免改造 + `MAX_ACTIVE` LRU。
2. **事件 topic 路由**：`Task.topic_id` + dispatch 标注 + `SystemEventBridge` 按 topic 注入。
3. **持久队列**：新表 + migration + 投递决策 + drain on spawn + push。
4. **迁移 + 集成测试**：serde default 兼容 + 跨块 e2e（串味回归 + zombie 补发回归）。

依赖序：块 1（池）是地基，块 2/3 依赖池的 `topic→分身` 查询，块 4 收口。块 2、3 在块 1 的
接口定下后可并行。

## 7. 非目标（YAGNI）

- 不做分身间跨 topic 记忆共享 / 全局摘要（用户明确否决，违背隔离目的）。
- 不做热门常驻 + 冷门懒加载的双策略（实现最复杂，懒启动+回收已够）。
- 不做跨节点分身（v1 home 单机；跨节点是另一条线）。
