# 绪论

## 1.1 研究背景及意义

AI Agent 是多智能体系统在大语言模型时代的新形态。传统多智能体研究强调自治实体之间的感知、通信、协商与协同，Wooldridge 在多智能体系统教材中给出的关于自治、社会能力、反应性与主动性的 Agent 定义 [@wooldridge2009mas]，以及 Stone 与 Veloso 在多智能体综述中对协调机制与学习适应能力的系统梳理 [@stone2000multiagent]，为后续 Agent 架构提供了理论基础。Russell 与 Norvig 在《人工智能：现代方法》中进一步将 Agent 概念抽象为「感知—决策—行动」闭环 [@russell2020aima]，使 Agent 概念在工程语境下具备清晰的可实现性。Jennings 在 2001 年的论文中指出，Agent 视角的根本价值在于「以自治实体为单元的高级抽象有助于管理复杂软件系统」[@jennings2001agentbased]。

大语言模型的成熟使 Agent 概念在工程实践中焕发新的活力。模型获得了以自然语言理解任务、以工具调用改变环境、以记忆模块保留经验的能力，使得 Agent 不再依赖手工编写的规则集。Wang 等人对基于大语言模型的自治 Agent 的综述将「规划、记忆、工具使用与行动反馈」归纳为现代 LLM-based agent 的四大核心组成 [@wang2023llmagentsurvey]。Yao 等人提出的 ReAct 框架将推理轨迹与外部行动交替生成，使模型能够在推理过程中调用环境反馈修正计划 [@yao2022react]；Schick 等人的 Toolformer 让模型自主学习何时调用 API、如何传入参数以及如何吸收结果 [@schick2023toolformer]；Karpas 等人的 MRKL 将大语言模型与外部知识源、符号推理模块组合，为「模型作为协调者，工具作为执行器」的系统结构提供了早期蓝本 [@karpas2022mrkl]。这些工作共同推动了 Agent 从纯语言生成向「推理—行动—观察」闭环的演进。因此，AI Agent 系统的研究对象已经从「单模型推理效果」扩展为「模型、工具、协议、运行时与观测系统共同构成的工程平台」。

在复杂软件开发、数据分析与自动化运维等场景中，单个 Agent 往往难以同时承担需求澄清、计划拆解、代码实现、测试验证与结果交付等职责。CAMEL 通过角色扮演方式研究通信 Agent 的协作能力 [@li2023camel]，AutoGen 将多 Agent 对话抽象为可编程的应用框架 [@wu2023autogen]，MetaGPT 将软件工程中的标准作业流程编码为多角色协作机制 [@hong2023metagpt]，AutoGPT 则探索了完全自主的目标分解与执行模式 [@significantgravitas2023autogpt]。这些工作说明，多 Agent 协作能够提高任务分解能力与过程可解释性，但也暴露出通信协议不统一、任务生命周期不清晰、状态难以追踪等工程问题。

对于本地化运行的 AI Agent 平台而言，高性能分布式通信具有直接的工程意义。第一，Agent 执行过程通常包含大量工具调用、文件读写、测试命令与中间消息，系统需要用低延迟通道将这些状态及时反馈给用户，否则用户无法判断 Agent 是在工作还是已经卡死。第二，多个 Agent 并发执行时，任务调度与消息回传必须避免轮询造成的延迟与资源浪费——轮询不仅放大延迟，还在 Agent 数量增长时导致控制流自身的可扩展性瓶颈。第三，AI Agent 的输出具有概率性，工程系统需要通过事件日志、会话恢复与执行隔离降低不可追溯风险。SWE-agent 在 Agent-Computer Interface 的研究中指出，面向 Agent 设计的接口与沙箱环境会显著影响软件工程任务的完成质量 [@yang2024sweagent]；OpenHands 进一步将 Agent 的执行环境视为通用平台问题 [@wang2024openhands]。由此可见，围绕 AI Agent 构建高性能通信底座，是使多 Agent 协作从实验演示走向可用系统的关键。

本文的研究意义在于，针对上述本地化、高性能、可观测的多 Agent 协作场景，设计并实现一套以事件驱动通信为核心的工程平台，验证「将通信底座作为一等公民设计」这一思路的工程可行性，并通过吞吐、延迟与压力测试给出可量化的性能边界。

## 1.2 国内外研究现状

从 Agent 行为模式来看，ReAct 提出将推理轨迹与外部行动交替生成 [@yao2022react]，是 LLM Agent 从纯语言生成迈向「推理—行动—观察」闭环的标志性工作；Toolformer 探索模型自主学习工具使用 [@schick2023toolformer]，使工具调用从人为示例引导变为模型内化的能力；MRKL 系统较早地将语言模型作为协调者、外部模块作为执行器进行组合 [@karpas2022mrkl]，为后续系统化 Agent 平台提供了思路。Voyager 在开放世界游戏中通过 skill library 持续积累与重用经验 [@wang2023voyager]，验证了「Agent 长期能力可以通过可检索、可组合的经验库形成」这一假设。这些工作共同推动了 Agent 从一次性脚本向具备规划、记忆与持续学习能力的自治执行单元转变。

从多 Agent 协作框架的角度来看，AutoGen [@wu2023autogen]、MetaGPT [@hong2023metagpt]、CAMEL [@li2023camel] 与 AutoGPT [@significantgravitas2023autogpt] 等系统主要围绕角色、对话与流程进行设计。AutoGen 强调可编程的多 Agent 对话抽象，使得 Agent 间的轮次、回合与终止条件可以被显式描述；MetaGPT 通过将软件工程的角色与流程编码进 Agent 协作机制，将多 Agent 协作的可控性大幅提升；CAMEL 关注 Agent 之间的角色扮演与对话演化机制；AutoGPT 则探索完全自主的任务分解与执行。这些系统证明了角色分工与任务链路的有效性，但多数系统以 Python 框架或云端应用为主要形态，通信层通常服务于上层协作逻辑，而非作为可独立审计、可回放、可跨节点扩展的底层平台来设计。

在 Agent 协议与编排层面，Anthropic 提出的 Model Context Protocol [@anthropic2024mcp] 试图标准化模型与外部工具、数据源之间的连接接口；Agent2Agent 协议则尝试用 AgentCard、Task、Message 与 Artifact 等概念描述独立 Agent 之间的互操作关系 [@a2aproject2025a2a]。两类协议解决的是不同层次的问题：MCP 关注模型与工具的接口规范，A2A 关注 Agent 与 Agent 之间的协作语义。本文工作在 A2A 与 MCP 兼容的基础上构建本地优先的通信底座，使二者各自发挥作用，避免协议层语义膨胀。

从更传统的分布式系统领域来看，多项经典工作为 Agent 通信系统提供了思想基础。Lamport 在 1978 年的论文中提出的逻辑时钟与事件因果序为分布式系统的时间观奠定了基础 [@lamport1978time]，至今仍是事件溯源、消息中间件与共识算法的理论起点。Dean 与 Ghemawat 提出的 MapReduce 证明了将大规模任务分解、调度与故障恢复封装到运行时中的工程价值 [@dean2004mapreduce]；Ghemawat 等人的 Google File System 强调了在廉价硬件上构建高吞吐、高可用存储系统的设计哲学 [@ghemawat2003gfs]。Kafka 以追加式日志为核心实现高吞吐消息处理 [@kreps2011kafka]，其「日志即一切」的思想直接影响了后续事件驱动系统的设计；Raft 通过更易理解的一致性协议降低了分布式状态复制的实现复杂度 [@ongaro2014raft]；ZooKeeper 与 Spanner 则在协调服务与全球一致性事务上分别提供了工业级实践 [@hunt2010zookeeper] [@corbett2012spanner]。这些工作虽然并非面向 AI Agent，但其关于任务调度、日志追加、故障恢复与一致性协议的思想，对 Agent 通信系统具有重要借鉴意义。

在工程实现层面，多个开源工具构成了本系统的技术基础。SQLite 通过 WAL 模式将事务写入追加式日志，在并发读写与崩溃恢复之间取得平衡 [@sqlite2024wal]；Tokio 的异步 channel 提供了 Rust 高并发系统中常用的消息传递基础，其中 broadcast 支持多生产者、多消费者的发布订阅模型 [@tokio2024broadcast]；Axum 提供了 Web 服务的中间件、路由、WebSocket 与 SSE 等核心能力 [@axum2024docs]；Git worktree 支持同一仓库下多个工作树并存，为 Agent 任务隔离提供了轻量级方案 [@git2024worktree]。WebSocket 协议 [@fette2011websocket] 与 Server-Sent Events 规范 [@whatwg2024sse] 则共同支撑了浏览器与服务端之间的实时通信。结合上述研究与工具，可以构建一种本地优先、事件驱动、可观测的 AI Agent 分布式通信平台。

综合来看，现有工作在 Agent 行为、协作框架与协议层面都有较为成熟的成果，但「将通信底座作为一等公民设计」的工作仍较为缺乏：多数系统的通信层是协作流程的副产物，缺乏可单独度量的性能指标与可独立审计的事件序列。本文工作正是针对这一空白展开，希望通过系统性的事件总线、形式化的延迟分解与可量化的吞吐评估，为后续多 Agent 系统的工程化提供可借鉴的基础设施。

## 1.3 论文的研究内容

本文设计并实现的 Fuxi 系统主要面向 AI Agent 多任务并行与分布式通信场景，重点研究内容包括以下五个方面。

第一，建立面向 AI Agent 的通信抽象。将用户意图、任务创建、任务派发、Agent 响应、工具调用与结果交付等运行时事件统一表示为可持久化的事件序列，使整个协作过程具备可观测、可回放、可审计的工程性质。

第二，设计「玄女—门客」分层协作模式。顶层 Agent 负责用户交互、任务判断与结果汇报，工作 Agent 负责具体执行。两类 Agent 通过编排层间接通信，避免直接调用造成的耦合，使任意一类 Agent 都可以被替换或并存。

第三，构建基于 Tokio broadcast 与 SQLite WAL 的事件总线。在同一抽象上同时承担实时分发、持久化与历史回放三项能力，使订阅者既能获取最新状态，又能在崩溃恢复或新订阅者上线时从历史出发继续工作。

第四，设计工作区隔离、角色加载、长期记忆、定时触发与 IM 接入等支撑模块。这些模块通过事件订阅与显式 API 与编排层交互，使系统在保持核心稳定的同时具备长期运行与跨平台观测能力。

第五，通过单元测试、集成测试、端到端验收与吞吐/延迟基准测试验证系统的可用性与性能。本文将系统的端到端延迟、吞吐与调度损耗等指标进行形式化定义，并通过多维实验给出可量化的性能边界。

根据当前代码实现，Fuxi 正文重点体现的模块包括：通信协议模块、事件总线模块、Agent 编排模块、分布式任务调度模块、执行适配器模块、工作区隔离模块、实时观测模块、记忆与经验模块、定时触发模块、交付物模块、IM/PWA 接入模块与测试评估模块。这些模块共同服务于一个目标：在多 Agent 并发工作时，以低延迟、可追溯、可恢复的方式完成任务通信与状态流转。

## 1.4 论文结构安排

本文按「问题—方案—实现—验证—回顾」五段式展开，共分为六章。

第一章为绪论。阐述 AI Agent 分布式通信系统的研究背景、国内外研究现状、研究内容与论文结构。

第二章为系统总体设计。分析系统的目标与功能/非功能需求，给出整体架构、通信模型形式化与性能指标定义，为后续模块设计与实验评估提供统一参照。

第三章为系统核心模块设计。分别说明通信协议、事件总线、编排调度、工作区隔离、观测、记忆与触发器七个核心模块的设计动机、关键接口与设计取舍。

第四章为系统实现。结合 Fuxi 代码仓库，说明 Rust workspace 的组织方式、事件数据结构、任务派发流程、分布式通信实现与关键流程伪代码。

第五章为系统测试与结果分析。介绍测试环境、测试用例覆盖、吞吐量、延迟、参数敏感性、事件总线压力等多维实验的设计与结果，并基于第二章的形式化指标进行定量分析。

第六章为总结与展望。总结本文工作并讨论分布式一致性、记忆机制、Agent 适配器、安全模型与用户界面五个方向的不足与后续优化路径。
