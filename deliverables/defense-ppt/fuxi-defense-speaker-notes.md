# Fuxi 毕业论文答辩讲稿提纲

答辩日期：2026-05-09  
题目：基于 AI Agent 的高性能分布式通讯系统

## 讲述主线

1. 开场：Fuxi 不是“再写一个多 Agent 聊天框架”，而是把多 Agent 日用化所需的通讯底座做成系统：事件、协议、隔离、观测。
2. 问题：现有多 Agent 框架多以 Python 角色对话为中心，跨进程通讯、任务生命周期、历史回放和实时观测较弱。
3. 目标：Rust、本地优先、事件驱动、可观测、可跨节点扩展。
4. 架构：A2A 是 Agent 间协作契约，EventBus 是系统事实流，两者正交。
5. 贡献：A2A 适配、非阻塞事件总线、玄女—门客分层、三层沙箱与 WS 反连、跨节点钩子化扩展。
6. 实验：合成任务剥离 LLM 推理，专门测编排和通讯层上限。
7. 结果：8 worker 665.00 tasks/s，16 worker 1288.24 tasks/s；task dispatch p50 32.93 ms；event_flow p99 0.26 ms；64 subscriber × 10k events/s 零丢帧。
8. 收束：Fuxi 的差异化在于把通讯底座从应用流程中显式剥离出来，而不是声称自己是最快或最通用的平台。

## 可能被问到的问题

**为什么已有 a2a-rs，还要自己实现 A2A 风格适配层？**  
不是因为 Rust 生态空白，而是因为本工作要把 A2A 的任务状态、流式事件和人工介入语义深度接进 Fuxi 的编排层与事件总线。论文里也明确说明当前实现沿用早期 binding，不主张已经完整兼容当前 v1.0。

**为什么实验用 10 ms sleep，不直接测真实 LLM 任务？**  
真实 LLM 任务主要受模型推理 1-30 秒主导，会掩盖通讯层差异。10 ms sleep 是为了隔离系统层开销，测编排和通讯路径的吞吐上限。论文中也明确限定了这个口径。

**事件总线为什么既要 broadcast 又要 SQLite WAL？**  
broadcast 服务实时观测，SQLite WAL 服务历史回放和审计。两者职责不同。Fuxi 的 publish 同时进入两条路径，拥塞时通过后台转交和 lag sentinel 让背压可见，而不阻塞调用方。

**玄女—门客听起来像命名设定，工程价值是什么？**  
工程价值是角色边界：玄女是唯一用户对话入口，门客是执行进程，所有门客协作都经编排层记录，避免 Agent 私下通讯导致事实流断裂。

**跨节点是否已经是完整分布式系统？**  
不是。当前是单机优先 + 扩展点验证，已跑通两节点 sandbox 和少量真实部署。10 节点以上、不可靠网络和故障转移是后续工作。

**系统安全性到什么程度？**  
已有三层 worktree sandbox 和跨节点 HMAC-SHA256 + nonce cache 验签。但工具调用授权、数据访问控制、提示注入防护仍不完整，这在局限页主动说明。
