## 这一版做了什么

- **整篇是一个故事, 不是 13 段讲解**。 主线是你自己的真实经历——凌晨两点三个 agent 撞车 → 我意识到缺什么 → 我做了什么 → 三个数字 → 我不假装它是什么。
- **嘴里几乎没有专业名词**。 屏幕上有 "broadcast / WAL / HMAC / trait" 这些词, 但你不读屏幕。 你说**屏幕背后的那层意思**。
- **每一项贡献都用一个生活比喻讲**——"流水账"、"秘书"、"独立小屋"、"主动找它说话"——这些比喻你自己讲完一遍就记住了, 不用背。
- **slide 切换跟语速同步**——不是讲完一段再点下一页, 是边讲下一句边切。 13 张 slide 在 5 分钟内自然走完。
- **答疑预案的答案也全大白话**, 你能用自己的话讲出来, 不是背技术名词。

## 怎么用

- **斜体小字** = 舞台动作, 不要念出来
- `(顿)` 半秒到一秒
- 加粗的话是**钩子句和 punch 句**, 必背 — 中间用自己语气讲
- 练 5 遍, 第 3 遍开始严格 5 分钟计时

## slide 11 · 数字之前 · 25 秒

*(切 slide 11, 看老师, 笑一下)*

讲数字之前, 我**自己先回答**一个老师必问的问题——

*(读屏幕, 慢)*

**为什么用 10 毫秒模拟任务, 不用真实大模型?**

*(顿)*

10 毫秒, 是 **worker 干活那一段时间** 的模拟——真实场景里这一段, 是大模型推理或调用工具, 1 到 30 秒。 **其他每一步, 都是 fuxi 的真实代码**。

*(顿)*

举个数学例子——8 个 worker 跑 800 个任务, **理论极限 1 秒, 我实测 1.2 秒**。 多出来的 **200 毫秒**, 就是我自己的传话和调度开销。

*(顿, punch)*

我用 10 毫秒, 是**故意把测试的尺子调精细**, 让我自己的损耗**显形**——不被大模型那 5 秒推理掩盖掉。

*(顿, punch)*

1. **第一遍** 通读 + 计时, 看是不是在 5 分 30 秒内。
2. **第二遍** 录音听回放, 检查有没有"嗯/那个/就是"这种 filler, 剔掉。
3. **第三遍** 上面 13 句加粗 punch **背下来**, 中间用自己的话过渡。
4. **第四遍** 不看稿, 看 deck 试讲一次, 严格 5 分钟计时, 记下卡壳点。
5. **第五遍** 对镜或对人, 完整讲一次, 看节奏 + 眼神 + 鞠躬时机。

**不要追求一字不差**。 追求 13 句 punch 立得住, 中间用自己的语气说话——**像跟人讲一个你刚发现的有趣故事**。

## 答疑预案 · 全部大白话版本

> 答疑 7-10 分钟会比主讲长, 老师会就 deck 上的技术词追问。 这里的答案我**全部用你能直接说出口的大白话**重写, 不是论文措辞。 听到对应问题, 用这个版本答。

---

**Q1 · 你说"agent 之间没有统一的话语"——已经有 a2a-rs 这个开源协议了, 为什么自己再写一遍?**

不是因为没人写过。 是因为我要**把"agent 需要等用户确认"这种状态, 接进我自己系统的内部**——这是把协议**接到平台层**的活, 不是把别人的客户端跑通就行。

我也写得很诚实——论文里说了, 我用的是这个协议**早期版本**, 不假装跟最新版完全兼容。

---

**Q2 · 为什么"记录每件事"要分两条路, 不能就一条?**

因为**一条路**, 既要给你实时看, 又要写进硬盘——拥塞的时候, 必然有一边吃亏。 要么**实时被拖慢**, 要么**写硬盘丢消息**。

两条同时, 各干各的, 互不耽误——这是我这次工作里, 我自己最坚持的一条。

---

**Q3 · "玄女""门客"这种命名听起来是不是噱头? 工程上有什么用?**

它的工程价值是**角色边界**——

"玄女"是用户唯一对话的对象。 任何 agent 之间的协作, **必须经过这个秘书统一记录**。 这一条硬规约, 让事实记录永远不断。

命名只是为了让规约**听起来更易记**。 代码里, "shutdown 玄女"这个函数名本身, 就提醒任何看代码的人:**这是规约的例外, 不是规约的延伸**。

---

**Q4 · 你说"两台机器跑通了"——这能算分布式吗?**

**坦白说, 不算完整分布式。**

我现在是单机优先, 加扩展点验证。 已经在两台机器和少量真实部署上跑通了端到端调度。

10 台机器以上、不可靠网络、节点挂了能不能转移——这是后续工作, 论文 §6.2 写明了。

---

**Q5 · 系统的安全做到什么程度?**

**已经有的**: 每个 agent 在独立小屋里干 (执行隔离), 跨机器之间的话**加签名 + 防重放 + 防时序攻击** (一套密码学标准动作)。

**还不完整的**: agent 调用工具的权限策略, 数据访问控制, 防别人在输入里偷偷塞指令 (prompt injection)。 这三块都在论文局限页**主动声明**了。

---

**Q6 · 你这个系统是只跑 demo, 还是真有人用?**

它是**我自己 ERP 项目的日常协作平台**, 跑了几个月。 不是答辩 demo。

论文最后一章我也写了——"**已在作者维护的 ERP 项目中作为日常协作平台运行**"。

---

**Q7 · 论文里写"五项贡献", 但 deck 上五张贡献页, 是不是有合并?**

没有合并。 deck 上 slide 06 到 slide 10, 一张一项, 跟论文五项贡献**严格一一对应**。

如果某一张 slide 内容看起来"分了两块" (比如沙箱 + 反向连), 那是因为这两块**在论文里就是同一项贡献的两个面**——多 agent 并发的两个具体痛点。

---

**Q8 · 你的 1288 次每秒, 跟 Kafka、NATS 这些成熟消息系统比怎么样?**

**不能直接比**, 也不应该比——

Kafka 是分布式持久队列, 走网络加磁盘, 处理的是**百万消息级**的数据流。
我这个东西是**单进程内的事件总线**, 走的是内存通道, 处理的是 **agent 编排层级**的事件。

应用场景、抽象层级、持久化语义都不一样。 我做的是 **agent 编排层的吞吐边界**, 不是消息中间件 benchmark。

---

**Q9 · 为什么用 Rust? 现在 agent 框架都是 Python 写的。**

正因为都 Python——

Python 的 GIL 让"不阻塞"这件事, 工程上**很难真正做到**。

Rust 的 async 加编译期所有权检查, 让"事件不丢""调用方不卡住"这种话, 从注释里的承诺, 变成了**编译期就检查的合同**。

性能是副产品, 主要是**正确性**——这一层基础设施需要你晚上能睡得着觉。

---

**Q10 · "玄女""门客"这种命名, 不会让代码可读性变差吗? 别人接手会看不懂吧?**

会, 我承认对外阅读门槛高了一点。

但内部协作上, 这两个名字成了**规约的载体**——`shutdown_xuannv_for_handoff` 这种函数名, 任何人 grep 一下就知道"这是规约的例外"。

**命名本身就是设计文档的一部分**。 这件事我在论文里专门解释过。

---

**Q11 · 你能详细讲一下 10 ms sleep 在整条链路里, 具体是哪一步吗? 测的时候 bench 走不走玄女?**

bench **不走玄女**——玄女是真实使用时跟用户对话的顶层 agent, 但 bench 直接绕过, 测 orchestrator 核心 + 一组 fake worker 的吞吐, 否则又把 LLM 推理变量混进来。

整条链路 8 步——

我从 bench 入口发任务 → orchestrator 收到 → 锁定一个空闲 worker → 通过 A2A HTTP 把任务发给那个 worker (走真实 axum + loopback) → **worker 在这一步 sleep 10 毫秒** → sleep 醒了, ack 一个 done 回去 → orchestrator 标完成 → 推到事件总线扇出给所有观察者。

**只有第 5 步是模拟的**, 模拟 agent 在干活——真实场景里这一步是大模型推理。 其他 7 步, **从 HTTP 往返、HMAC 签名、Tokio 调度、SQLite 写入到事件扇出**, **每一步都是 fuxi 的真实代码**, 真实开销。

数学上验证一下——8 worker 跑 800 个任务, 每个真跑 10 毫秒, 完美并行理论极限是 1 秒。 我实测 1.2 秒。 多出来的**200 毫秒, 就是 fuxi 自己 7 步的开销**, 损耗 ~17%。

如果换真实大模型, 每个任务 5 秒, 那 200 毫秒 / 5 秒 = 4%, 就**测不出来**了。 我故意用 10 ms, 是**让自己的开销显形**, 不是为了让数字好看。

---

**Q12-pre · 你这个测试是不是太理想化了? 不就是函数调用开销吗?**

**测的不是纯函数调用**——HTTP 往返、HMAC 签名、Tokio 调度、SQLite 磁盘写入, **都是真实 syscall**, 走真实生产代码。

但确实是**单进程 + 本机 loopback** —— 没有跨机器网络延迟, 也没有真实大模型。 worker 那一步用 10 毫秒 sleep 替代 LLM, 其他每一步都是生产代码。

这套 setup 给的是**通讯层在最干净条件下的上限**。 加上跨机器网络, 数字会下降; 加上真实大模型, 我自己 23 毫秒的传话开销在端到端占比就显得不重要了——但**这层开销得先量出来**, 否则你不知道做优化做到哪儿才够。

学术上这种 setup 叫 "**in-process integration benchmark**", 介于单元测试和生产压测之间。

---

**Q11.5 · 64×10k 零丢帧, broadcast buffer 调到 32k 是怎么定的? production 也用 32k 吗?**

**先澄清一点 — 32k 是 bench 专门加大的, production 默认 1024**, 这两个值用途不一样。

**32k 的定法**: **320 毫秒容忍窗口** —— 32 768 slots ÷ 100 000 events/s = 0.32 秒。 留这个窗口是因为 Tokio 调度抖动 + cache miss 偶发超 100 毫秒, 16k slots (160ms) 会被这种抖动误伤; 64k slots (640ms) 太宽, broadcast buffer 越大内存复制成本越高。 **32k 是这两者的中值, 经验调出来的**。

**production 为什么 1024 就够**: 真实工作负载是 1-5 sub × 100-1000 events/s, 1024 ÷ 1000 = **1 秒容忍窗口**, 远超调度抖动余量。 bench 加大到 32k **不是为了让数字好看**, 是为了**把测试条件推到极端**, 看 fuxi 在 100k/s × 64 sub 这种极端组合下扛不扛得住。

**主动声明边界**: 64×10k 零丢帧的数字, 反映的是 **buffer 配到 32k 时**的能力。 100k/s + 64 sub 这一格 (再压一个数量级) buffer 满了就会出 drops——我在论文里也写了, 不假装"任何参数下都零丢"。

**Q12 · 那 32.93 ms 这个 p50 派发延迟, 具体怎么拆解?**

我在论文里给了**工程估算**——这是基于代码细节的归因, 没经过 profiler 独立验证, 我会诚实说出来——

- HTTP 往返 ~10 ms
- HMAC 签名 ~1 ms
- Tokio 异步任务调度 ~5 ms
- SQLite 状态写 ~6 ms
- 调度器内部任务匹配 ~4 ms
- worker 接收事件 + 反序列化 + ack ~7 ms

加起来大致 33 毫秒。 跟 p50 实测 32.93 ms 对得上。

p99 是 36.66 ms, **p99 / p50 = 1.11**——尾部抖动可控, 没有偶发的卡顿。
