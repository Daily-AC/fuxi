\section{绪论}

伏羲是一套以 Rust 实现的本地优先 AI Agent 编排平台。它把用户的自然语言意图、顶层 Agent 玄女的对话决策、多个并发执行的门客（基于 Claude Code 与 Codex 等 headless agent CLI 启动的工作进程）以及它们之间的协作消息，统一视作可观测、可回放、可审计的事件序列；通过单一 SQLite WAL 真相源、Tokio broadcast 实时分发与 Google A2A v1.0 协议互通三套基础设施，把多 Agent 系统从「演示脚本」推到「日用平台」。本章梳理伏羲所处的技术语境、相关研究与同类系统现状，明确论文要解决的问题与五条具体贡献，并给出全文的章节安排。

\subsection{研究背景及意义}

AI Agent 在 2023 年之后再度成为系统层面的研究焦点。Wooldridge 在多 Agent 系统教材中给出的「自治、社会能力、反应性、主动性」四属性定义~\parencite{wooldridge2009mas} 为 Agent 抽象提供了长期稳定的理论基础；Russell 与 Norvig 在《人工智能：现代方法》中把 Agent 进一步抽象为「感知—决策—行动」闭环~\parencite{russell2020aima}，让 Agent 具备明确的工程实现路径。在大语言模型成熟之后，这一抽象层次使 Agent 概念被迅速工程化。

大模型让 Agent 具备了过去十年没有的能力——以自然语言理解任务、以工具调用改变环境、以记忆模块累积经验。Wang 等人对 LLM-based 自治 Agent 的综述把现代 Agent 抽象为「规划、记忆、工具使用与行动反馈」四个组件~\parencite{wang2023llmagentsurvey}；Yao 等人提出的 ReAct 框架把推理轨迹与外部行动交替生成，使模型能在过程中根据观察修正计划~\parencite{yao2022react}；Schick 等人的 Toolformer 让模型自主学习工具调用~\parencite{schick2023toolformer}；Karpas 等人的 MRKL 系统把语言模型作为协调者、外部模块作为执行器组合到一起~\parencite{karpas2022mrkl}。在这一系列工作之后，AI Agent 的研究对象不再是单模型推理效果，而是「模型、工具、协议、运行时与观测系统共同构成的工程平台」。Voyager 在开放世界游戏中通过 skill library 持续积累与重用经验~\parencite{wang2023voyager}，进一步表明 Agent 的能力可以跨任务沉淀；SWE-agent 在软件工程任务上指出，面向 Agent 设计的接口与沙箱环境会显著影响最终完成质量~\parencite{yang2024sweagent}；OpenHands 把 Agent 的执行环境视为通用平台问题~\parencite{wang2024openhands}。这些工作共同表明，要让 Agent 真正承担起复杂任务的执行责任，必须把工具接口、执行隔离与持续记忆当成一等公民设计，而不是把它们作为对话循环的附属物。

在工程使用场景中，单个 Agent 难以同时承担需求澄清、计划拆解、代码实现、测试验证与结果交付等所有职责，这一观察推动了多 Agent 协作工作的兴起。CAMEL 通过角色扮演研究 Agent 之间的对话演化~\parencite{li2023camel}；AutoGen 把多 Agent 对话抽象为可编程框架~\parencite{wu2023autogen}；MetaGPT 把软件工程的标准作业流程编码为多角色协作~\parencite{hong2023metagpt}；AutoGPT 探索完全自主的目标分解与执行~\parencite{significantgravitas2023autogpt}。这些系统证明了多 Agent 协作能够提高任务分解能力与过程可解释性，但也暴露出三类共性工程问题：通讯协议不统一，每个框架自定义对话或消息格式，跨框架复用门客困难；任务生命周期不清晰，许多框架只在 Python 进程内维护状态，进程一退出全部上下文丢失；状态难以追踪，运行时的轮询逻辑、消息分发与工具调用混在同一进程内，外部观察者只能从最终输出反推过程，无法独立审计或回放历史。

对一个本地化运行、要被日用的多 Agent 平台而言，高性能分布式通讯不是可选锦上添花，而是平台能否成立的前提。第一，Agent 在执行过程中会产生密集的工具调用、文件读写、命令执行与中间消息。系统必须用低延迟通道把这些状态及时反馈给用户，否则用户无从判断 Agent 是在工作还是已经卡死——伏羲实测的事件总线广播 p99 延迟为 0.26 ms（见第 5 章表~\ref{tab:latency}），任务派发链路 p99 为 36.66 ms，正是这一约束的工程兑现。第二，多个 Agent 并发执行时，任务调度与消息回传必须避免轮询造成的延迟与资源浪费——这条原则在伏羲被升级成「公理 3：真实时不轮询」，所有观察组件必须订阅事件总线而不是周期性查询数据库；早期版本中 CLI 子进程对玄女 ID 做 5 分钟一次轮询的设计被改成 \texttt{tokio::sync::watch}，感知延迟从分钟级压到毫秒级。第三，AI Agent 的输出具有概率性，工程系统需要通过事件日志、会话恢复与执行隔离来降低不可追溯风险。这一点与 Lamport 在 1978 年提出的「分布式系统中事件因果序」思想~\parencite{lamport1978time} 在工程上对应：一个看不到事件历史的多 Agent 系统，等同于一个没有时钟的分布式系统，任何调试与验收都失去基础。

需要在此明确「工具」与「平台」的边界。一个 Agent 工具——例如某个支持工具调用的 LLM 客户端、某个 prompt 链式调用框架——通常解决「让单个 Agent 完成更复杂任务」的问题；而一个 Agent 平台需要解决「让多个 Agent 长期协作并被人类持续观察」的问题。前者关心模型与工具如何在一次会话内拼装；后者关心多 Agent 如何在数小时甚至数天的时间跨度上协调任务、共享上下文、对外报告进度。这两类问题的解空间并不一样：工具层可以容忍状态在内存里、可以容忍消息在控制台输出，但平台层必须把状态写到持久化日志、必须让消息可以被多个订阅者并发消费、必须让任意时刻的系统截面可以被外部观察者重建。本文把伏羲明确定位为「平台」，因此设计目标里写入了「事件可回放」「观测不轮询」「跨节点可扩展」等约束，这些约束在「工具」层级的研究里通常不被讨论。

2024 年以来，headless agent CLI 的兴起进一步把上述需求具象化。Anthropic 的 Claude Code、OpenAI 的 Codex CLI、Google 的 Gemini CLI 等工具以 \texttt{claude -p}、\texttt{codex exec} 这类「把整段任务作为一次性提示送入、把过程事件流式输出」的形态投入实际生产；它们不再是 Web 界面上的对话框，而是可以被 shell 脚本、CI 流水线、定时任务或上层 Agent 调用的标准化执行单元。这一形态的兴起改变了「多 Agent 协作」的工程定义——协作不再是同一进程内多个对象的相互调用，而是多个独立子进程之间通过结构化消息相互调度。这恰好与分布式系统中「以消息为契约、以进程为隔离单元」的传统工程范式重合，意味着多 Agent 平台的设计可以也应该参考过去四十年分布式系统积累的工程智慧——而不是把所有协调逻辑都重新塞进单个 Python 进程里。

综合上述背景可以得出本文研究的工程意义：在多 Agent 概念已经具备充分理论铺垫、且 LLM agent CLI（Claude Code、Codex、Gemini CLI）已经成为工程世界的客观存在的当下，缺的不是「下一个 prompt 框架」，而是一个把 Agent 协作的通讯底座作为一等公民设计、能在普通笔记本电脑上稳定承载日常工作流、并在多节点之间可信扩展的平台。本文设计与实现的伏羲系统正是面向这一需求展开，并通过吞吐、延迟与压力测试给出可量化的性能边界。

为方便后续章节阅读，此处先约定本文使用的若干术语。系统的顶层调度 Agent 一律称「玄女」，对应实现为 \texttt{fuxi-orchestrator} crate；执行任务的工作 Agent 一律称「门客」，具体适配器为 \texttt{fuxi-agent-cc}（Claude Code）与 \texttt{fuxi-agent-codex}（OpenAI Codex）。事件分发抽象在中文叙述中称「事件总线」，对应代码标识符为 \texttt{EventBus}。系统名「伏羲」与 crate 前缀 \texttt{fuxi-} 同指本工作。「通讯」一词贯穿全文，与论文题目保持一致。Google 主导的 Agent2Agent 协议简称 A2A，Anthropic 的 Model Context Protocol 简称 MCP，二者面向不同语义层次：前者描述 Agent 间协作，后者描述模型与工具的接口。

\subsection{国内外研究现状}

围绕 AI Agent 编排已经形成了几条互相平行的研究路线。第一条线是以 ReAct~\parencite{yao2022react}、Toolformer~\parencite{schick2023toolformer}、MRKL~\parencite{karpas2022mrkl} 为代表的 Agent 行为模式，关注单 Agent 在「推理—行动—观察」闭环中的能力上限；这条线的代表工作把 Agent 从一次性脚本推进为具备规划与工具使用能力的自治执行单元，但通讯层一般退化为 Python 函数调用，不涉及跨进程协作。Voyager 通过 skill library 把单 Agent 的能力沉淀到长期记忆中~\parencite{wang2023voyager}，伏羲的角色玉牒（\texttt{fuxi-skills}）借鉴了这一「技能沉淀」思路，但加入了 staging 与 ledger 双轨审阅以适配多用户场景。

第二条线是多 Agent 协作框架。AutoGen~\parencite{wu2023autogen} 强调可编程的对话抽象，让轮次、回合与终止条件能被显式描述；MetaGPT~\parencite{hong2023metagpt} 把软件工程角色与流程编码进协作机制；CAMEL~\parencite{li2023camel} 关注 Agent 间角色扮演与对话演化；AutoGPT~\parencite{significantgravitas2023autogpt} 探索完全自主的任务分解。这些系统证明了角色分工与任务链路的有效性，但绝大多数以 Python 框架或云端 SaaS 为主要形态，通讯层通常是协作流程的副产物：消息在同一 Python 进程内通过函数调用传递，状态保存在进程内的对象图中，进程退出意味着会话结束。这种设计使框架本身无法独立审计、无法跨节点扩展、也无法承载长期任务（如一次跑数小时的代码迁移）。SWE-agent~\parencite{yang2024sweagent} 与 OpenHands~\parencite{wang2024openhands} 把 Agent 的执行环境提升为研究对象，明确了沙箱与接口设计的重要性，但它们的执行模型仍是单 Agent 单进程，没有处理多门客并发、跨进程通讯与本地多节点这类工程问题。2024 年之后这条路线进一步演化：AutoGen 升级到 v0.4 后把多 Agent 抽象重塑为独立的 AgentOS 形态~\parencite{ag2_2024}，ChatDev~\parencite{qian2024chatdev} 把软件开发流程切分为多角色对话流水线，CrewAI~\parencite{crewai_2024} 在工程社区中广泛被用于角色驱动的任务编排——这些工作仍延续 Python 平台 + 角色对话的主流路线，与本文的 Rust 平台 + 跨进程门客 + 跨节点 A2A 路线在底层实现选择上明确分叉。

第三条线是 Agent 协议与编排标准。Anthropic 在 2024 年提出的 Model Context Protocol~\parencite{anthropic2024mcp} 试图标准化模型与外部工具、数据源之间的连接接口；Google 主导的 Agent2Agent 协议~\parencite{a2aproject2025a2a} 用 \texttt{AgentCard}、\texttt{Task}、\texttt{Message} 与 \texttt{Artifact} 等概念描述独立 Agent 之间的互操作语义。两类协议解决的是不同层次的问题：MCP 关注模型与工具的接口规范，A2A 关注 Agent 与 Agent 之间的协作语义。MCP 已有官方 SDK 与生态。A2A 已有 Python、Go、Java、JavaScript、.NET 与 Rust（\texttt{a2a-rs}）六个语言的官方 SDK，Rust 生态内还有 \texttt{a2a-client}、\texttt{a2a-types} 等第三方 crate 提供独立的协议封装。本工作不依托「Rust 生态空白」立论，而是面向「与本地优先编排层和事件总线深度集成、并扩展 InputRequired 人工介入语义」这一具体场景，从零实现一份与 fuxi 平台同源演进的 A2A 子集——这一定位正是本文的切入点。

第三条线之外，与本工作直接相邻的还有 LLM 推理服务的系统层研究——例如 Parrot~\parencite{lin2024parrot} 在 OSDI 2024 上提出的「Semantic Variable」抽象把 LLM 应用语义传到推理服务以共享上下文与并行执行。这类工作与 Fuxi 的关注点正交但互补：Parrot 关心「单次推理在 GPU 集群上如何被高效服务」，Fuxi 关心「多轮 Agent 协作在本地多进程之间如何被可观测地编排」。

第四条线是分布式系统与消息中间件领域的经典工作。Lamport 关于逻辑时钟与事件因果序的开创性论文~\parencite{lamport1978time} 至今仍是事件溯源、消息中间件与共识算法的理论起点；Kafka 以追加式日志为核心实现高吞吐消息处理~\parencite{kreps2011kafka}，「日志即一切」的思想直接影响了后续事件驱动系统的设计。这些工作虽然不针对 AI Agent，但其关于追加式日志、事件因果序、push 式消息分发与故障恢复的思想，在伏羲的事件总线设计中被反复借鉴——伏羲的 \texttt{EventBus} 同时承担「实时分发、持久化、历史回放」三件事，其底层正是「broadcast push 通道 + WAL append-only 日志」的组合，对应于 Kafka 的 push 模式和 SQLite 的 WAL 实现~\parencite{sqlite2024wal}。本文后续章节在涉及具体工程模式时还会借鉴 MapReduce~\parencite{dean2004mapreduce}、Raft~\parencite{ongaro2014raft}、ZooKeeper~\parencite{hunt2010zookeeper} 等系统的局部思想，相关引用就近给出，此处不再罗列。

工程实现层面的可用工具构成了本系统的技术基础：Tokio 提供了 Rust 异步运行时与 broadcast、mpsc 等 channel 原语~\parencite{tokio2024broadcast}；Axum 提供了基于 \texttt{tower}/\texttt{hyper} 的 Web 框架，支持 WebSocket 与 SSE~\parencite{axum2024docs}；Git worktree 支持同一仓库下多个工作树并存，为门客任务隔离提供了轻量级方案~\parencite{git2024worktree}；WebSocket 协议~\parencite{fette2011websocket} 与 Server-Sent Events 规范~\parencite{whatwg2024sse} 共同支撑了浏览器与服务端之间的实时双向/单向通讯。这一技术栈的组合，使得在 Rust 上构建一个多 Agent 通讯平台不需要从最底层重新发明 IO 框架。

在 Rust 生态内部，与 Agent 编排相邻的工作主要集中在异步运行时、消息中间件与 Web 框架等基础设施层——例如 Tokio 异步运行时与 \texttt{sync::broadcast} 多生产者多消费者通道~\parencite{tokio2024broadcast}、Axum 模块化 Web 框架~\parencite{axum2024docs}——但它们都是通用基础设施而非 Agent 平台。围绕 LLM 的 Rust 库（如 \texttt{llm-chain}、\texttt{rig}、\texttt{kalosm}）数量有限，绝大多数停留在「单 Agent 调模型 + 工具调用」层级，没有覆盖多 Agent 协作、跨节点调度或事件溯源这类系统级议题。换言之，Rust 中已有可靠的「积木」可拿来即用，但仍缺少把这些积木组装成完整多 Agent 平台的系统级工作——本文的设计正面向这一需求展开。

从横向比较来看，AutoGen、MetaGPT、CAMEL、AutoGPT、OpenHands 这一组同类工作并不是「不好」——它们各自在自己的研究问题上做出了扎实贡献。但从「把通讯底座作为一等公民」的视角来看，这些系统普遍存在三个共性盲区：其一，Python 中心带来的运行时局限——Python 的 GIL 与同步异步混合模型让单进程无法充分利用多核，多 Agent 并发本质上仍是协程切换，跨进程通讯几乎全部回退到子进程 stdio 的非结构化文本交互；其二，单进程状态丢失——上下文存在 Python 对象图里，进程崩溃意味着所有对话历史与中间状态消失，没有持久化的事件序列可以重放；其三，没有跨节点能力——这些系统假定运行在单台机器或单个云端实例，没有在「家庭多机部署」「跨节点调度」「负载均衡」这些场景中进行设计。伏羲选择 Rust 工作区 + 多进程门客 + 跨节点 A2A 这一组合是有意识地避开上述盲区：用 Rust 拿到无 GIL 的多核并发与可预测的内存布局，用多进程门客获得故障隔离与跨工作区调度的灵活度，用 A2A 协议的 wire 形态把 Agent 间通讯标准化以便未来与第三方实现互通。这套组合并不是要替代上述工作，而是在它们划定的语义层之下，补一层缺失的工程基础设施。

\subsection{研究目标与贡献}

本文的研究目标是：在 Rust 工作区中实现一个本地优先、事件驱动、可观测、可跨节点扩展的多 AI Agent 协作平台，把通讯底座作为一等公民设计，并通过吞吐、延迟与压力测试给出可量化的性能边界。围绕这一目标，本文做出以下五项可独立审视的工程贡献。

\textbf{贡献一：与 fuxi 平台同源演进的 A2A v1.0 实现}。Agent2Agent 协议是 Google 主导、Linux Foundation 维护的 Agent 间协作开放标准~\parencite{a2aproject2025a2a}。当前生态已有 Python、Go、Java、JavaScript、.NET 与 Rust（\texttt{a2a-rs}）六个语言的官方 SDK，以及 \texttt{a2a-client}、\texttt{a2a-types} 等若干第三方 crate。本工作选择从零实现 \texttt{fuxi-a2a} crate（共 1321 行，其中核心实现 1063 行、端到端测试 258 行），原因不在协议结构本身——通用 SDK 已可满足协议覆盖度需求——而在于本文需要把 A2A 与 fuxi 的事件总线、玄女—门客编排层和反向 WebSocket sandbox 三者深度耦合，这一耦合面在通用 SDK 中不存在。\texttt{fuxi-a2a} 沿用早期 A2A JSON-RPC binding，覆盖 \texttt{agent/getCard}、\texttt{tasks/send}、\texttt{tasks/sendSubscribe}、\texttt{tasks/get}、\texttt{tasks/cancel} 五条核心路径，对应 agent discovery、task send、task stream、task query 与 task cancel 这一最小可用闭环——足以承载 Fuxi 当前的多门客协作场景。在此基础上，本工作的差异化贡献集中在两点：一是把 A2A 规范已有的 \texttt{input-required} 中间态从协议字段提升为平台级人工介入信号——映射到 Fuxi 内部 \texttt{Task::PendingApproval} 与 \texttt{ShelfStatus::AwaitingInput}，使「门客在等用户」相对「门客在工作」对编排器、调度器与多端观测都成为可见状态；二是采用单端点 HTTP+SSE 设计——所有方法共用 \texttt{POST /a2a} 端点，流式方法在响应阶段升级为 \texttt{text/event-stream}，避免客户端管理两条独立连接的复杂度。需要说明的是，本实现采用早期 A2A JSON-RPC 形态，与当前官方规范 PascalCase 方法命名（\texttt{SendMessage}、\texttt{GetTask} 等）和 \texttt{Part} one-of 字段语义并不完全对齐，亦未与官方 \texttt{a2a-rs} SDK 做完整 wire-level 互通测试；本文不主张「v1.0 兼容」，而是把贡献定位在与平台深度集成与人工介入语义的工程映射上。

\textbf{贡献二：非阻塞事件总线与 lag 哨兵机制}。\texttt{fuxi-events} crate 实现了一个把「实时分发、持久化、历史回放」三件事统一在同一抽象内的事件总线。其核心创新点是\texttt{publish()} 路径上的「\texttt{try\_send} + 后台转交 + 哨兵告警」三步组合：广播路径用 Tokio broadcast 零拷贝扇出给所有订阅者；持久化路径用 \texttt{try\_send} 投递到 mpsc 队列，拥塞时不阻塞调用方而是后台 spawn 任务承担等待；当 writer 待处理数超过 \texttt{lag\_threshold = 512} 阈值时，发出一条可观测的 \texttt{Custom \{ "event\_store\_lagged" \}} 哨兵事件，让运维侧把背压从「不可见的死锁」看成「可见的告警」。该设计兼顾了「调用方永不阻塞」与「事件不丢」这两个看似矛盾的约束，是对 Kafka 经典 push 模式~\parencite{kreps2011kafka} 在本地优先场景下的工程化适配。

\textbf{贡献三：玄女—门客分层与不可绕过的编排层}。系统在 Agent 角色上确立顶层调度 Agent（玄女）与执行 Agent（门客）的显式分工。玄女是用户对话面唯一入口，所有门客之间的通讯必须经过玄女知情，且任何调度决策都必须发出对应事件让观测端透明可追。这条「编排层不可绕过」的硬约束在 \texttt{Fuxi::shutdown\_agent} 等敏感操作中被反复实施：一切 shutdown 路径必须比对玄女 \texttt{AgentId}，命中则 warn 并 noop 返回，例外仅限显式命名为 \texttt{shutdown\_xuannv\_for\_handoff} 的会话交接路径——名字本身就是约束，让 grep 能一眼看出禁止其他位置调用。Worker 选择函数沿「角色匹配、节点钉死、最低饱和度」三层过滤逐级缩小候选集，思路与 MapReduce~\parencite{dean2004mapreduce}「数据本地性 + 负载均衡」相通而更轻量。本设计与 MetaGPT~\parencite{hong2023metagpt}基于角色分工的多 Agent 协作思想方向一致，但把「编排层不可绕过」从隐含规约提升为代码层硬强制。

\textbf{贡献四：三层沙箱 \texorpdfstring{$\times$}{x} WebSocket 反连门客执行模式}。多 Agent 并发执行的两个核心工程难题分别是文件系统隔离与进程间双向通讯。本文针对前者提出 L1/L2/L3 三层沙箱模型（\texttt{WorkspaceLayer::L1ReadOnly}、\texttt{L2Ephemeral}、\texttt{L3Persistent}）：L1 是项目源码与依赖的只读视图，所有门客共享；L2 是任务级临时 worktree，每次 \texttt{dispatch} 创建独立分支、任务结束自动清理，依赖 git 原生的 \texttt{worktree} 机制~\parencite{git2024worktree} 提供互不干扰的工作树；L3 是角色级持久沙箱，让同一角色跨任务复用 \texttt{target/}、\texttt{node\_modules/} 等编译产物。针对后者，本文提出 WS 反连模式——编排层在本机启动 WebSocket 服务器，子进程启动时通过 \texttt{--sdk-url ws://127.0.0.1:<port>/ws/cli/<sid>} 反向连接回来，使编排层在任意时刻都可主动推送 \texttt{send\_message} 或 \texttt{cancel}，而不必等门客 poll stdio。这两项设计共同把「多 Agent CLI 适配」收敛到一个统一框架，已成功支持 Claude Code 与 Codex 两套差异极大的 headless agent CLI。

\textbf{贡献五：跨节点扩展点的钩子化抽象与 sandbox 验证}。在不破坏单机部署稳定性承诺的前提下，本文把跨节点协作所需的四个扩展点抽象为依赖反转 trait：\texttt{RecallSink} 让长期记忆把召回结果回传给编排层、\texttt{DistEnqueuer} 让任务在跨节点路径上由 controller 入队、\texttt{NodeLoadProvider} 让 auto-pin 在多节点之间按 \texttt{inflight / max\_concurrency} 比值选择最闲节点、\texttt{ExtractorSpawner} 让记忆抽取器在合适时机被启动。四个 trait 统一定义在低层 crate（\texttt{fuxi-core}/\texttt{fuxi-orchestrator}/\texttt{fuxi-memory}），具体实现由顶层 \texttt{fuxi-cli} 在 daemon 启动时注入，避开了「memory 反向依赖 orchestrator」之类的循环依赖；这套依赖反转范式同时是本文规避 Rust workspace 循环依赖的标准做法。\texttt{Project} 数据结构新增 \texttt{host\_nodes: Vec<String>} 字段标记项目可执行节点，配合 \texttt{auto\_pin\_from\_project} 入口的双保险守卫保证用户显式 \texttt{@<node>} 不被自动逻辑覆盖，新增字段以 \texttt{\#[serde(default)]} 搭配 \texttt{project\_meta\_deserializes\_legacy\_without\_host\_nodes} 反回归测试保持跨版本兼容。当前实现已在两节点 sandbox 与少量真实跨机部署中跑通端到端调度，更高节点数与不可靠链路下的故障转移验证留待后续工作（详见 §6.2 局限与不足）。

上述五项贡献并非互相独立的孤岛，而是围绕同一核心命题——「把 Agent 间通讯的契约、事实流、调度边界与执行隔离同时做对」——从协议层到平台层逐级展开的工程承担：贡献一在协议层把 Agent 间契约语义标准化；贡献二在事实层把系统内部状态以可观测、可回放的事件流忠实记录；贡献三在控制层确立编排不可绕过的硬约束；贡献四在执行层把文件隔离与进程间双向通讯抽象为统一框架；贡献五在扩展层把跨节点能力以 trait 钩子的形式预留出来。本文最终交付一份 13 crate、约 8.25 万行 Rust 代码的可执行工作区，配套 1363 个单元测试、27 个集成测试与持续运行于作者维护的 ERP 项目代码库的真实业务验证；这份「工程兑现」是上述五项设计在真实代码与真实使用场景上同时成立的证据，但本身不作为独立贡献项列出。

\subsection{论文组织结构}

全文按「问题—方案—实现—验证—回顾」五段式展开，共分六章。

\textbf{第一章 绪论}（本章）。阐述 AI Agent 分布式通讯系统的研究背景、国内外研究现状、研究目标与五项工程贡献，并给出全文的章节安排。

\textbf{第二章 系统总体设计}。从功能性需求与非功能性需求出发，给出伏羲的整体分层架构与通讯模型形式化定义，明确事件驱动、单一真相源、不可绕过编排三条系统级公理，并定义吞吐量、端到端延迟与调度损耗等性能指标的形式化表达，为后续模块设计与实验评估提供统一参照。

\textbf{第三章 系统核心模块设计}。沿依赖自下而上的顺序，把 13 个 crate 的内部设计逐一展开，覆盖通讯协议（A2A wire 层与 \texttt{input-required} 状态在平台层的映射）、事件总线（broadcast 与 WAL 双路径架构）、编排调度（玄女—门客分层与 worker 选择函数）、执行适配器（cc/codex 差异与 WS 反连）、工作区隔离（L1/L2/L3 三层沙箱）、观测与 IM 接入、记忆与角色玉牒等七大设计单元；每个模块附带「关键设计决策与取舍」段落，把当时讨论过却未采用的备选方案与放弃理由一并记录。

\textbf{第四章 系统实现}。从 daemon 启动开始，沿事件流走完一次完整的「玄女接收任务 $\to$ 分派给门客 $\to$ 门客通过 A2A 回报 $\to$ 事件总线持久化 $\to$ IM 端实时刷新」的全链路执行轨迹，把第三章的接口在实际调用栈上一一对应，并展开 \texttt{fuxi-a2a} crate 从 wire 层到 SSE 流的全部实现细节。

\textbf{第五章 系统测试与结果分析}。沿正确性、实时性、吞吐扩展性、参数敏感性、通讯层压力承受五个维度组织实验，覆盖单元测试与集成测试覆盖、基础吞吐量、延迟分布与尾部、\texttt{poll\_ms} 参数敏感性、事件总线纯压测等多组测量；所有数据基于 Apple Silicon、macOS 25.0、Rust stable、Tokio 多线程运行时之上完成，吞吐采用 5-run median、延迟采用 500 样本统计 p50/p99；并对每组数字给出物理意义层面的解释，避免实验章退化为单纯数据登记。

\textbf{第六章 总结与展望}。回顾全文工作并讨论分布式一致性、记忆机制语义召回、Agent 适配器横向扩展、安全模型与用户界面五个方向的不足与后续优化路径。

\subsection{本章小结}

本章从 Agent 理论与 LLM 工程化两条历史线索出发，明确了「把通讯底座作为一等公民」这一论文核心立场；横向考察了行为模式、协作框架、协议标准与分布式系统经典工作四条相关研究路线，指出现有同类系统在 Python 中心、单进程状态、跨节点缺失三个方面的共性盲区；给出本文的研究目标与五项工程贡献——面向 Fuxi 本地优先协作场景的 A2A v1.0 核心闭环实现、非阻塞事件总线与 lag 哨兵、玄女—门客分层与不可绕过的编排层、三层沙箱与 WS 反连、跨节点扩展点的钩子化抽象与 sandbox 验证；最后概述全文的六章结构。下一章将从功能与非功能需求出发，把上述贡献映射到具体的系统模块边界与形式化指标定义，为后续章节的展开提供统一参照。
